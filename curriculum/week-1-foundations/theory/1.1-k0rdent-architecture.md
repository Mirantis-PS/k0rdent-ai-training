## 1. Introduction to k0rdent Enterprise

### What is k0rdent?

k0rdent Enterprise is Mirantis's solution for managing Kubernetes at scale. It provides a unified platform for deploying, managing, and monitoring Kubernetes clusters across multiple infrastructure providers—from bare metal servers to cloud VMs to managed Kubernetes services.

k0rdent enables service providers and enterprises to build AI infrastructure products:

| Product | Description |
|---------|-------------|
| **BMaaS** | Bare Metal as a Service - Hardware rental and utilization |
| **VMaaS** | Virtual Machines as a Service - VM provisioning on Kubernetes |
| **KaaS** | Kubernetes as a Service - Managed cluster provisioning |
| **MaaS** | Models as a Service - LLM endpoints with API keys and billing |

### The Problem k0rdent Solves

Organizations operating Kubernetes at scale face several challenges:

**Cluster Sprawl and Inconsistent Configurations**
- Teams deploy clusters with different configurations
- No standardization across environments
- Configuration drift over time

**Complex Day-2 Operations**
- Upgrades require manual coordination
- Scaling decisions made ad-hoc
- No unified tooling across clusters

**Lack of Visibility**
- No "single pane of glass" — one unified console for all clusters — for fleet health
- Metrics scattered across monitoring systems
- Cost attribution is difficult

**Manual, Error-Prone Provisioning**
- Each cluster deployment is a custom project
- No reusable templates
- Credentials managed inconsistently

### k0rdent Value Proposition

k0rdent addresses these challenges through:

**Unified Control Plane**
- Single management interface for all clusters
- Consistent API across infrastructure providers
- Centralized credential management

**Declarative Cluster Lifecycle**
- Clusters defined as Kubernetes custom resources
- GitOps-friendly workflow
- Automated reconciliation

**Built-in Observability and FinOps**
- Integrated metrics and logging
- Cost visibility per cluster and tenant
- Resource utilization tracking

**Multi-Cloud and Hybrid Support**
- AWS, Azure, GCP, vSphere, OpenStack, bare metal (Metal3), and more via CAPI
- Consistent experience across providers
- Single template works everywhere

## 2. Architecture Overview

### The Complete Picture

Before breaking k0rdent down piece by piece, it helps to see the whole system at once. The diagram below maps everything covered in this module and the next: who drives the platform (left), what runs inside the management cluster (centre), the child clusters it provisions (below), and the infrastructure it provisions them onto (right).

![k0rdent architecture overview. Platform roles and interfaces on the left submit a desired state definition to a central management cluster containing KCM, KSM, KOF, Templates, and Security/Access. The management cluster provisions the child clusters shown below it and the target infrastructure on the right, spanning AWS, Azure, GCP, vSphere, OpenStack, and bare metal. A six-step simplified flow runs along the bottom.](../../images/k0rdent-architecture.png)

**In words:** Reading the diagram from left to right:

- **Users and interfaces (left).** Three roles drive the platform. The *Platform Architect* designs platforms and templates; the *Platform Lead / CloudOps* manages clouds and configures RBAC, credentials, and providers; *Platform Engineers / project teams* deploy clusters and consume services. All three reach k0rdent through the same four interfaces — the k0rdent UI, `kubectl`, GitOps/YAML, or the API — and what they submit is a **desired state definition**, never an imperative command.

- **Management cluster (centre)** — the heart of the system, holding five labelled areas:
  - **A. KCM** orchestrates the cluster lifecycle. It wraps the CAPI controllers, the infrastructure providers (AWS, Azure, GCP, vSphere, OpenStack, bare metal/SSH), k0smotron for bootstrap and hosted control planes, and the RemoteMachine provider for SSH and edge targets.
  - **B. KSM** manages state, services, and applications: the services controller, day-2 operations (upgrade, scale, teardown), and add-ons and workloads — reconciling continuously rather than one-shot.
  - **C. KOF** centralises observability and FinOps: metrics, logs, traces, cost analytics, and OpenTelemetry.
  - **D. Templates** hold the reusable blueprints — `ClusterTemplate` for clusters, `ServiceTemplate` for services and add-ons — all parametrizable, reusable, and immutable.
  - **E. Security / Access** binds a Cluster-Identity secret into a Credential and scopes access with RBAC per namespace. The Platform Lead creates the identity and credential; teams only ever *reference* the credential, and Secret payloads are base64-encoded, not encrypted by that encoding. RBAC limits access; encryption at rest requires separate configuration.

- **Child clusters (below).** Clusters A and C are **standalone** — each runs its own control plane (API server, etcd, controllers) on dedicated nodes. Cluster B uses a **hosted control plane**: its control plane runs as pods inside the management cluster, managed by k0smotron. Every cluster carries its own applications, ingress, monitoring, logging, network policies, and storage classes, and all of them are isolated from each other *and* from the management cluster.

- **Target environments (right).** A common ClusterDeployment API uses provider-specific templates and configuration for AWS, Azure, GCP, VMware/vSphere, OpenStack, or bare metal and edge.

- **Simplified flow (bottom).** The six numbered steps trace a single request end to end: an engineer references a ClusterTemplate/ServiceTemplate → references an authorized Credential → KCM plus CAPI provision the infrastructure and cluster → k0smotron provisions a hosted control plane if one was requested → KSM deploys services, add-ons, and applications → KOF centralises the resulting metrics, logs, traces, and costs.

- **Arrow colours.** Solid blue is network/API traffic and management-cluster provisioning, green is service deployment, solid red is telemetry flowing back from the workloads, dashed red is identities and credentials, and dashed purple is templates and definitions.

The **Hosted Control Plane** callout on the right states the tradeoff directly, and it is worth registering early: if the management cluster becomes unavailable, existing workloads keep running, but management of them is impacted. [Deployment Model](#deployment-model) below returns to this shared failure domain.

### Deployment Model

k0rdent uses a **hub-spoke** architecture. The Management Cluster is the hub, and every Workload Cluster it provisions is a spoke — reached through Cluster API, never configured directly. [The Complete Picture](#the-complete-picture) above shows the full topology; this section covers the division of responsibility between the two kinds of cluster.

**Management Cluster:**
The Management Cluster is the control hub that runs k0rdent components. It:
- Runs k0rdent Enterprise (KCM, KSM, KOF)
- Stores cluster definitions and state as CRDs
- Orchestrates provisioning operations via CAPI
- Typically runs on k0s (lightweight Kubernetes)
- Does NOT run application workloads

**Workload Clusters:**
Workload Clusters are the clusters where applications run. They:
- Run actual business applications
- Can be any Kubernetes distribution
- Are managed declaratively via CRDs on the Management Cluster
- Report metrics back to KOF
- Can span multiple cloud providers

**Hosted Control Plane Mode:**
In addition to the standard model where workload cluster control planes run on dedicated VMs, k0rdent supports a **Hosted Control Plane** mode via k0smotron. In this mode, the control plane runs as pods on the management cluster itself — only worker nodes are provisioned as VMs. This reduces cost and speeds up provisioning, but creates a shared failure domain. See [Theory 1.2 — k0smotron](1.2-k0rdent-components.md) for details.

### API-First Design

k0rdent follows Kubernetes-native patterns:
- All operations are performed via CRDs
- kubectl is the primary interface
- API server handles authentication/authorization
- Controllers reconcile desired state

## 3. Core Components Deep Dive

### 3.1 k0rdent Cluster Manager (KCM)

**Purpose:** Deployment and lifecycle management of Kubernetes clusters

**Key Responsibilities:**
- **Cluster Provisioning:** Deploy clusters across any supported CAPI provider (AWS, Azure, GCP, vSphere, OpenStack, Metal3, and more)
- **Day-2 Operations:** Upgrades, scaling, node repairs, rollbacks
- **Template Management:** Reusable cluster configurations
- **Credential Management:** Secure storage and rotation of cloud credentials

**Key CRDs:**

| CRD | Purpose |
|-----|---------|
| `Management` | Core k0rdent configuration object |
| `ClusterDeployment` | Defines a cluster to be provisioned |
| `ClusterTemplate` | Reusable cluster configurations |
| `Credential` | Cloud provider authentication |

**Example ClusterDeployment:**
```yaml
apiVersion: k0rdent.mirantis.com/v1beta1
kind: ClusterDeployment
metadata:
  name: production-cluster
  namespace: kcm-system
spec:
  template: aws-standalone-cp-1-0-28   # a versioned ClusterTemplate name
  credential: aws-cluster-identity-cred
  config:
    region: us-east-1
    controlPlaneNumber: 3
    controlPlane:
      instanceType: m5.xlarge
    workersNumber: 4
    worker:
      instanceType: m5.2xlarge
```

> You'll work with these exact fields hands-on in Lab 1.5. Template versions vary between releases — discover the ones available in your environment with `kubectl get clustertemplates -n kcm-system`.

*Where you'll use this: you provision a cluster with KCM in Lab 1.5 and upgrade with it in Lab 1.8.*

### 3.2 k0rdent State Management (KSM)

**Purpose:** Installation and lifecycle management of services deployed to clusters

**Key Responsibilities:**
- **Service Deployment:** Install applications and operators to workload clusters
- **Helm Chart Management:** Version-controlled chart deployments
- **GitOps Integration:** Sync configurations from Git repositories
- **Multi-Cluster Rollouts:** Deploy services across fleet with staged rollouts

**Use Cases:**
- Deploy GPU Operator to all GPU-enabled clusters
- Install monitoring stack consistently
- Roll out security patches across fleet
- Manage service catalog offerings

*Where you'll use this: you deploy services across clusters with KSM's MultiClusterService in Lab 1.7.*

### 3.3 k0rdent Observability and FinOps (KOF)

**Purpose:** Cluster monitoring, events, logs, and cost management

**Key Responsibilities:**
- **Monitoring:** Collect and visualize metrics from all clusters
- **Log Aggregation:** Centralize logs for troubleshooting
- **Alerting:** Unified alerting across the fleet
- **Cost Visibility:** Track spend by cluster, tenant, and workload
- **Resource Optimization:** Identify underutilized resources

**Integrations:**
- VictoriaMetrics for metrics collection, storage, and querying
- VictoriaLogs for log aggregation
- OpenTelemetry for telemetry collection (metrics, logs, traces)
- VictoriaTraces for distributed tracing — OTel-native trace storage (exposes a Jaeger-compatible query API, so existing Jaeger UIs and tooling still work)
- Grafana for visualization
- OpenCost for Kubernetes cost analysis

*Where you'll use this: you install KOF and explore its dashboards in Lab 1.6.*

## 4. Relationship with Cluster API (CAPI)

### What is Cluster API?

Cluster API is a Kubernetes sub-project that provides declarative APIs for cluster creation, configuration, and management. It uses the Kubernetes controller pattern to manage cluster lifecycle.

**Key Concepts:**
- **Cluster:** The top-level resource representing a Kubernetes cluster
- **Machine:** A single node (control plane or worker)
- **MachineDeployment:** Manages a set of machines (like Deployment for pods)
- **Infrastructure Provider:** Provider-specific implementation (AWS, Azure, etc.)

### How k0rdent Uses CAPI

k0rdent is built on top of CAPI, providing an opinionated, production-ready implementation:

```
┌─────────────────────────────────────┐
│         k0rdent Enterprise          │
│  ┌─────────────────────────────┐   │
│  │ ClusterDeployment           │   │  ← k0rdent abstraction
│  │ ClusterTemplate             │   │
│  │ Credential                  │   │
│  └─────────────┬───────────────┘   │
│                │                    │
│  ┌─────────────▼───────────────┐   │
│  │      Cluster API Core       │   │  ← CAPI primitives
│  │  Cluster, Machine, etc.     │   │
│  └─────────────┬───────────────┘   │
│                │                    │
│  ┌─────────────▼───────────────┐   │
│  │   Infrastructure Providers  │   │  ← Provider implementations
│  │  CAPA, CAPZ, CAPG, CAPV,   │   │
│  │  CAPO, CAPM3, and more      │   │
│  └─────────────────────────────┘   │
└─────────────────────────────────────┘
```

**In words:** The diagram shows three layers stacked inside k0rdent Enterprise, with each layer driving the one below it. At the top are the k0rdent abstractions (ClusterDeployment, ClusterTemplate, Credential). These translate down into Cluster API core primitives (Cluster, Machine, and so on), which in turn invoke the infrastructure providers at the bottom (CAPA, CAPZ, CAPG, CAPV, CAPO, CAPM3, and more) that perform the actual provider-specific provisioning.

**k0rdent adds value on top of CAPI:**
- Simplified UX with ClusterTemplates
- Integrated credential management
- Built-in observability
- Multi-tenant support
- Service catalog integration

### Infrastructure Providers

| Provider | CRD Prefix | Use Case |
|----------|------------|----------|
| CAPA (AWS) | `AWSCluster` | AWS EC2-based clusters (+ EKS managed) |
| CAPZ (Azure) | `AzureCluster` | Azure VM-based clusters (+ AKS managed) |
| CAPG (GCP) | `GCPCluster` | Google Cloud clusters (+ GKE managed) |
| CAPV (vSphere) | `VSphereCluster` | VMware vSphere clusters |
| CAPO (OpenStack) | `OpenStackCluster` | OpenStack private cloud clusters |
| CAPM3 (Metal3) | `Metal3Cluster` | Bare metal via Ironic |
| CAPK (KubeVirt) | `KubevirtCluster` | VM workloads on Kubernetes |

> **Note:** AWS, Azure, GCP, vSphere, and OpenStack have validated ProviderTemplates and pre-built ClusterTemplates that ship with k0rdent. Metal3 (Week 2) and KubeVirt (Week 3) are supported via additional setup. Since k0rdent is built on CAPI, any infrastructure with a CAPI provider can be integrated via custom ProviderTemplates.

## 5. k0rdent in the Mirantis Ecosystem

### Related Products

**k0s (Kubernetes Distribution)**
- Lightweight, single-binary Kubernetes
- Used as the default distribution for Management Clusters
- Can also be used for Workload Clusters
- Zero dependencies, easy to operate

**Mirantis Kubernetes Engine (MKE)**
- Enterprise Kubernetes platform
- Can be managed by k0rdent as a workload cluster type
- Provides additional enterprise features

**Mirantis Secure Registry (MSR)**
- Container image registry
- Integrated with k0rdent for secure image supply chain
- Vulnerability scanning and signing

### Deployment Topology

```
┌─────────────────────────────────────────────────────────────┐
│                     Provider Infrastructure                   │
│                                                              │
│  ┌────────────────┐                                         │
│  │ Management     │  k0s + k0rdent Enterprise               │
│  │ Cluster        │  (KCM, KSM, KOF, CAPI)                  │
│  └───────┬────────┘                                         │
│          │                                                   │
│  ┌───────┴───────────────────────────────────┐              │
│  │                                           │              │
│  ▼                   ▼                       ▼              │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐    │
│  │ Tenant A │  │ Tenant B │  │ Tenant C │  │ Tenant D │    │
│  │ Cluster  │  │ Cluster  │  │ Cluster  │  │ Cluster  │    │
│  │ (k0s)    │  │ (k0s)    │  │ (EKS)    │  │ (Metal3) │    │
│  └──────────┘  └──────────┘  └──────────┘  └──────────┘    │
│       │              │              │              │         │
│       └──────────────┴──────────────┴──────────────┘         │
│                   Managed by k0rdent                         │
└─────────────────────────────────────────────────────────────┘
```

**In words:** The diagram shows a single Management Cluster — running k0s plus k0rdent Enterprise (KCM, KSM, KOF, CAPI) — at the top of the provider's infrastructure. Below it, the management cluster fans out to four tenant clusters: Tenant A and Tenant B run k0s, Tenant C runs EKS, and Tenant D runs on bare metal via Metal3. All four tenant clusters, regardless of distribution or infrastructure, are managed by the one k0rdent management cluster above them.

## Knowledge Check

1. What are the three core components of k0rdent Enterprise?
2. What is the difference between a Management Cluster and a Workload Cluster?
3. Which component is responsible for cluster provisioning?
4. What role does Cluster API play in k0rdent?
5. Name three infrastructure providers supported by k0rdent.
6. What problems does k0rdent solve for organizations?
7. How does KSM differ from KCM in its responsibilities?

<details>
<summary><strong>Answer Key</strong> (click to expand)</summary>

1. **KCM** (Cluster Manager), **KSM** (State Management), and **KOF** (Observability & FinOps).
2. The **Management Cluster** runs k0rdent components and orchestrates provisioning -- it does NOT run application workloads. **Workload Clusters** run actual business applications and are managed declaratively from the management cluster.
3. **KCM** (k0rdent Cluster Manager), which uses Cluster API under the hood.
4. CAPI provides the declarative APIs and controller pattern for cluster lifecycle management. k0rdent builds on top of CAPI, adding simplified UX (ClusterTemplates), credential management, multi-tenancy, and observability.
5. Any three of: **CAPA** (AWS), **CAPZ** (Azure), **CAPG** (GCP), **CAPV** (vSphere), **CAPO** (OpenStack), **CAPM3** (Metal3/bare metal), **CAPK** (KubeVirt). AWS, Azure, GCP, vSphere, and OpenStack have validated ProviderTemplates; Metal3 and KubeVirt are supported via additional setup. More providers can be added via CAPI's extensible provider model.
6. Cluster sprawl and inconsistent configurations, complex Day-2 operations, lack of fleet visibility, and manual error-prone provisioning.
7. **KCM** manages cluster infrastructure lifecycle (provisioning, upgrades, scaling). **KSM** manages services and applications deployed *to* those clusters (Helm charts, GitOps, multi-cluster rollouts).
