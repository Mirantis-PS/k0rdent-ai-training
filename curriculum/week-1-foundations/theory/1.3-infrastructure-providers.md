## 1. Introduction to Cluster API (CAPI)

### What is Cluster API?

Cluster API is a Kubernetes project that provides declarative APIs and tooling to simplify provisioning, upgrading, and operating Kubernetes clusters.

**Key Concepts:**
- **Declarative**: Define clusters as Kubernetes resources (CRDs)
- **Consistent**: Same workflow across different infrastructure providers
- **Extensible**: Provider model allows support for any infrastructure

### CAPI Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                    Management Cluster                        │
│                                                             │
│  ┌───────────────┐   ┌───────────────┐   ┌───────────────┐  │
│  │ Core CAPI     │   │ Bootstrap     │   │ Control Plane │  │
│  │ Controllers   │   │ Provider      │   │ Provider      │  │
│  │               │   │ (e.g., k0s)   │   │ (e.g., k0s)   │  │
│  └───────────────┘   └───────────────┘   └───────────────┘  │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐    │
│  │            Infrastructure Provider                   │    │
│  │  (CAPA, CAPZ, CAPG, CAPV, CAPO, CAPM3, etc.)      │    │
│  └─────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────┘
```

### Provider Types

| Type | Responsibility | Examples |
|------|----------------|----------|
| **Infrastructure** | Provision compute resources | CAPA (AWS), CAPZ (Azure), CAPG (GCP), CAPV (vSphere), CAPO (OpenStack), CAPM3 (Metal3), CAPK (KubeVirt) |
| **Bootstrap** | Initialize Kubernetes nodes | k0s, kubeadm |
| **Control Plane** | Manage control plane lifecycle | k0s, kubeadm |

## 2. Infrastructure Providers Supported by k0rdent

### Cloud and Virtualization Providers

#### AWS (CAPA)

**Use Cases:**
- Production workloads on AWS EC2
- Auto-scaling worker pools
- Integration with AWS services (EBS, ELB, etc.)

**Required Credentials:**
- AWS Access Key ID
- AWS Secret Access Key
- (Optional) Session Token for temporary credentials

**Key Features:**
- Multi-AZ deployment support
- Spot instance support for cost savings
- EBS volume provisioning
- VPC and security group management

#### Azure (CAPZ)

**Use Cases:**
- Production workloads on Azure VMs
- Hybrid scenarios with Azure Arc
- Integration with Azure Active Directory

**Required Credentials:**
- Service Principal or Managed Identity
- Subscription ID
- Tenant ID
- Client ID and Client Secret (for Service Principal)

**Key Features:**
- Azure Resource Manager (ARM) integration
- Availability Zone deployment
- Azure CNI networking support
- Managed Identity for workload identity
- Azure Disk CSI driver integration

**Azure Secret Configuration:**
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: azure-credentials
  namespace: kcm-system
type: Opaque
stringData:
  AZURE_SUBSCRIPTION_ID: "<subscription-id>"
  AZURE_TENANT_ID: "<tenant-id>"
  AZURE_CLIENT_ID: "<client-id>"
  AZURE_CLIENT_SECRET: "<client-secret>"
```

**Azure Identity Reference:**
```yaml
apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
kind: AzureClusterIdentity
metadata:
  name: cluster-identity
  namespace: kcm-system
spec:
  type: ServicePrincipal
  tenantID: "<tenant-id>"
  clientID: "<client-id>"
  clientSecret:
    name: azure-credentials
    namespace: kcm-system
  allowedNamespaces: {}
```

#### vSphere (CAPV)

**Use Cases:**
- On-premises data center deployments
- VMware-based private cloud
- Hybrid cloud with VMware Cloud on AWS

**Required Credentials:**
- vCenter Server URL
- Username and password
- (Optional) Certificate thumbprint or CA bundle

**Key Features:**
- VM template cloning
- Distributed virtual switch support
- Storage policy integration
- vSphere HA compatibility
- GPU passthrough for AI workloads

**vSphere Secret Configuration:**
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: vsphere-credentials
  namespace: kcm-system
type: Opaque
stringData:
  username: "administrator@vsphere.local"
  password: "<password>"
```

**vSphere Cluster Identity:**
```yaml
apiVersion: infrastructure.cluster.x-k8s.io/v1beta1
kind: VSphereClusterIdentity
metadata:
  name: vsphere-identity
  namespace: kcm-system
spec:
  secretName: vsphere-credentials
  allowedNamespaces:
    selector:
      matchLabels: {}
```

**vSphere-Specific ClusterDeployment Values:**
```yaml
spec:
  config:
    vsphere:
      server: vcenter.example.com
      datacenter: DC1
      datastore: datastore1
      network: VM Network
      resourcePool: kubernetes
      folder: /DC1/vm/kubernetes
      template: /DC1/vm/templates/ubuntu-2204-kube-v1.32
```

#### GCP (CAPG)

**Use Cases:**
- Production workloads on Google Compute Engine
- Integration with GKE and Google Cloud services
- Multi-cloud strategies alongside AWS/Azure

**Required Credentials:**
- GCP Service Account key (JSON)
- Project ID

**Key Features:**
- Regional and zonal cluster support
- Preemptible VM support for cost savings
- Persistent Disk CSI integration

#### OpenStack (CAPO)

**Use Cases:**
- Private cloud deployments on OpenStack infrastructure
- Sovereign cloud and data residency requirements
- Telco and edge deployments

**Required Credentials:**
- OpenStack `clouds.yaml` configuration
- Application credentials or username/password

**Key Features:**
- Nova instance provisioning
- Neutron networking integration
- Cinder volume support
- Octavia load balancer integration

> **Note:** AWS, Azure, GCP, vSphere, and OpenStack have validated ProviderTemplates and pre-built ClusterTemplates that ship with k0rdent. Metal3 (Week 2) and KubeVirt (Week 3) are supported via additional setup. Since k0rdent is built on Cluster API, any infrastructure with a CAPI provider can be integrated via custom ProviderTemplates.

### Bare Metal Provider

#### Metal3 (CAPM3)

Metal3 became a CNCF Incubating project in August 2025, establishing it as the standard for bare metal Kubernetes provisioning.

**Use Cases:**
- Bare metal Kubernetes clusters
- Edge deployments
- High-performance AI/ML workloads
- GPU clusters requiring NVLink connectivity

**Architecture Overview:**

```
┌─────────────────────────────────────────────────────────────┐
│                   Management Cluster                         │
│                                                             │
│  ┌──────────────────┐    ┌──────────────────┐              │
│  │  Bare Metal      │    │  Cluster API     │              │
│  │  Operator (BMO)  │◄──►│  Provider Metal3 │              │
│  └────────┬─────────┘    └──────────────────┘              │
│           │                                                 │
│           ▼                                                 │
│  ┌──────────────────┐                                      │
│  │     Ironic       │                                      │
│  │  (Provisioning)  │                                      │
│  └────────┬─────────┘                                      │
│           │                                                 │
└───────────┼─────────────────────────────────────────────────┘
            │ BMC API (Redfish/IPMI)
            ▼
┌─────────────────────────────────────────────────────────────┐
│                    Bare Metal Host                          │
│                                                             │
│  ┌──────────────────┐                                      │
│  │  Ironic Python   │  ◄── Runs during provisioning        │
│  │  Agent (IPA)     │                                      │
│  └──────────────────┘                                      │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**Integration with Ironic:**

Metal3 uses OpenStack Ironic as its provisioning engine. Ironic handles:

1. **Hardware Discovery:** Introspects bare metal hosts to catalog CPU, memory, storage, and NICs
2. **Image Deployment:** Writes OS images to target disks via the Ironic Python Agent (IPA)
3. **BMC Communication:** Manages power state and boot order via Redfish or IPMI
4. **Network Boot:** Coordinates PXE/UEFI HTTP boot for initial ramdisk loading

**Provisioning State Machine:**

```
                    ┌──────────────┐
                    │  Registering │
                    └──────┬───────┘
                           │
                           ▼
┌──────────────┐    ┌──────────────┐
│   Available  │◄───│  Inspecting  │
└──────┬───────┘    └──────────────┘
       │
       │ Provision requested
       ▼
┌──────────────┐
│ Provisioning │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  Installing  │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  First-Boot  │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│    Ready     │
└──────────────┘
```

**BMC Protocols:**

| Protocol | Description | Use Case |
|----------|-------------|----------|
| Redfish | Modern REST API over HTTPS | Preferred for new hardware |
| IPMI | Legacy binary protocol | Older servers |
| iDRAC | Dell-specific | Dell PowerEdge servers |
| iLO | HPE-specific | HPE ProLiant servers |

**BareMetalHost CRD Example:**

```yaml
apiVersion: metal3.io/v1alpha1
kind: BareMetalHost
metadata:
  name: gpu-node-1
  namespace: metal3
spec:
  online: true
  bootMACAddress: 00:5c:52:31:3a:9c
  bmc:
    address: redfish-virtualmedia://192.168.1.100/redfish/v1/Systems/1
    credentialsName: gpu-node-1-bmc-secret
    disableCertificateVerification: true
  image:
    url: http://images.example.com/ubuntu-22.04.qcow2
    checksum: http://images.example.com/ubuntu-22.04.qcow2.md5sum
    checksumType: md5
    format: qcow2
  userData:
    name: gpu-node-1-user-data
    namespace: metal3
```

> **Note:** Metal3 is covered in depth in Week 2: Bare Metal as a Service

## 3. Credential Management

### Security Model

k0rdent uses Kubernetes Secrets to store sensitive credentials, referenced by `Credential` CRDs.

```
┌─────────────────┐     ┌──────────────────────┐     ┌─────────────────┐     ┌──────────────┐
│   Credential    │────▶│  Provider Identity   │────▶│     Secret      │────▶│ Cloud        │
│   (CRD)         │     │  (e.g. AWSCluster-   │     │ (actual creds)  │     │ Provider API │
│                 │     │   StaticIdentity)    │     │                 │     │              │
└─────────────────┘     └──────────────────────┘     └─────────────────┘     └──────────────┘
```

### Creating Credentials (AWS Example)

k0rdent uses a three-layer credential model for cloud providers:

| Layer | Resource | Purpose |
|-------|----------|---------|
| 1 | Kubernetes `Secret` | Stores actual cloud credentials |
| 2 | Provider Identity CRD | Provider-specific identity configuration |
| 3 | k0rdent `Credential` | References the identity, used by ClusterDeployments |

#### Step 1: Create the Secret

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: aws-cluster-identity-secret
  namespace: kcm-system
type: Opaque
stringData:
  AccessKeyID: "AKIA..."
  SecretAccessKey: "..."
```

#### Step 2: Create the Provider Identity

Each cloud provider has its own identity CRD:

```yaml
apiVersion: infrastructure.cluster.x-k8s.io/v1beta2
kind: AWSClusterStaticIdentity
metadata:
  name: aws-cluster-identity
  namespace: kcm-system
spec:
  secretRef: aws-cluster-identity-secret
  allowedNamespaces:
    selector:
      matchLabels: {}
```

#### Step 3: Create the k0rdent Credential

```yaml
apiVersion: k0rdent.mirantis.com/v1beta1
kind: Credential
metadata:
  name: aws-cluster-identity-cred
  namespace: kcm-system
spec:
  identityRef:
    apiVersion: infrastructure.cluster.x-k8s.io/v1beta2
    kind: AWSClusterStaticIdentity
    name: aws-cluster-identity
    namespace: kcm-system
```

**Provider Identity CRDs by Provider:**

| Provider | Identity CRD | Secret Keys |
|----------|-------------|-------------|
| AWS | `AWSClusterStaticIdentity` | `AccessKeyID`, `SecretAccessKey` |
| Azure | `AzureClusterIdentity` | `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, etc. |
| vSphere | `VSphereClusterIdentity` | `username`, `password` |
| Remote | *(none -- Credential references Secret directly)* | SSH private key |

> **Note:** The RemoteMachine provider is the exception -- its Credential references a Secret directly without an intermediate identity CRD.

### Best Practices

- **Least Privilege**: Create credentials with minimum required permissions
- **Rotation**: Plan for credential rotation
- **Secrets Management**: Consider external secrets managers (Vault, AWS Secrets Manager)
- **Namespace Isolation**: Keep credentials in appropriate namespaces

### IAM Policy Requirements (AWS)

CAPA requires specific AWS permissions to provision and manage EC2 instances, networking, and load balancers. The policy below represents the minimum required permissions:

**Required Permissions by Category:**

| Category | Actions | Purpose |
|----------|---------|---------|
| EC2 | `ec2:Describe*`, `ec2:RunInstances`, `ec2:TerminateInstances` | Instance lifecycle |
| VPC | `ec2:CreateVpc`, `ec2:CreateSubnet`, `ec2:CreateRouteTable` | Network provisioning |
| ELB | `elasticloadbalancing:*` | Control plane load balancer |
| IAM | `iam:GetRole`, `iam:PassRole`, `iam:CreateInstanceProfile` | Instance roles |
| S3 | `s3:GetObject` | Image retrieval (optional) |

**Recommended Policy:**

## 4. Cluster Templates by Provider

### AWS Templates

k0rdent includes pre-built templates for AWS:

| Template | Description | Use Case |
|----------|-------------|----------|
| `aws-standalone-cp-*` | Single control plane node | Dev/test environments |
| `aws-hosted-cp-*` | Hosted control plane (CP as pods) | Production workloads |

> **Note:** Template names include version suffixes (e.g., `aws-standalone-cp-1-0-20`). The exact name depends on your k0rdent version. Always discover available templates with:
> ```bash
> kubectl get clustertemplates -n kcm-system | grep aws
> ```

### Template Structure

Templates are the building blocks of k0rdent's declarative cluster provisioning. Each template wraps a Helm chart that contains the CAPI resources needed to provision a cluster.

```yaml
apiVersion: k0rdent.mirantis.com/v1beta1
kind: ClusterTemplate
metadata:
  name: aws-standalone-cp-<version>  # e.g., aws-standalone-cp-1-0-20
  namespace: kcm-system
spec:
  providers:
    infrastructure: aws
    bootstrap: k0s
    controlPlane: k0s

  # Helm chart reference for cluster resources
  helm:
    chartSpec:
      chart: aws-standalone-cp
      version: 0.1.0
      sourceRef:
        kind: HelmRepository
        name: k0rdent-templates
        namespace: kcm-system

  # CAPI contract versions this template supports
  capiContracts:
    - infrastructure-v1beta2
    - bootstrap-v1beta1
    - controlplane-v1beta1
```

**Template Components:**

| Field | Description |
|-------|-------------|
| `spec.providers` | Declares which CAPI providers the template uses |
| `spec.helm.chartSpec` | References the Helm chart containing CAPI manifests |
| `spec.capiContracts` | API versions the template is compatible with |

### Customizing Templates

You can create custom templates based on existing ones by following these steps:

**Step 1: Export an Existing Template**

```bash
# Get the template definition
kubectl get clustertemplate <TEMPLATE_NAME> -n kcm-system -o yaml > my-custom-template.yaml
```

**Step 2: Modify the Template**

```yaml
apiVersion: k0rdent.mirantis.com/v1beta1
kind: ClusterTemplate
metadata:
  name: aws-gpu-cluster-0-1-0  # New unique name
  namespace: kcm-system
spec:
  providers:
    infrastructure: aws
    bootstrap: k0s
    controlPlane: k0s
  helm:
    chartSpec:
      chart: aws-standalone-cp
      version: 0.1.0
      sourceRef:
        kind: HelmRepository
        name: k0rdent-templates
        namespace: kcm-system
      # Override default values for GPU workloads
      valuesFrom:
        - kind: ConfigMap
          name: gpu-cluster-values
          namespace: kcm-system
```

**Step 3: Create a Values ConfigMap**

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: gpu-cluster-values
  namespace: kcm-system
data:
  values.yaml: |
    worker:
      instanceType: p3.8xlarge
      rootVolumeSize: 200
    controlPlane:
      instanceType: m5.xlarge
```

**Step 4: Apply the Template**

```bash
kubectl apply -f my-custom-template.yaml
```

**Template Inheritance Pattern:**

```
┌────────────────────┐
│  Base Template     │  ← Provided by k0rdent
│  (aws-standalone)  │
└─────────┬──────────┘
          │
          ▼
┌────────────────────┐
│  Custom Template   │  ← Your customizations
│  (aws-gpu-cluster) │
└─────────┬──────────┘
          │
          ▼
┌────────────────────┐
│ ClusterDeployment  │  ← Instance-specific values
└────────────────────┘
```

## 5. Provider Configuration Workflow

### Enabling a Provider

```bash
# 1. Create the secret with credentials
kubectl apply -f aws-credentials-secret.yaml

# 2. Create the Credential resource
kubectl apply -f aws-credential.yaml

# 3. Update Management object to enable provider
kubectl edit management kcm -n kcm-system
```

### Verifying Provider Status

```bash
# Check if provider controllers are running
kubectl get pods -n kcm-system | grep capa

# Check provider status
kubectl get providers -n kcm-system

# View available templates for the provider
kubectl get clustertemplates -n kcm-system | grep aws
```

## 6. Multi-Cloud Strategy

### When to Use Multiple Providers

k0rdent's multi-provider architecture enables sophisticated deployment strategies:

| Strategy | Description | Use Case |
|----------|-------------|----------|
| **Geographic Distribution** | Clusters in multiple regions/clouds | Global applications, data residency |
| **Hybrid Cloud** | On-prem + public cloud | Sensitive data on-prem, burst to cloud |
| **Provider Diversity** | Workloads across AWS/Azure/GCP | Vendor risk mitigation |
| **Cost Optimization** | Spot instances + reserved capacity | Balance cost and availability |

### Consistency Across Clouds

k0rdent ensures consistency through:

**1. Unified API**
```yaml
# Same ClusterDeployment structure regardless of provider
apiVersion: k0rdent.mirantis.com/v1beta1
kind: ClusterDeployment
spec:
  template: <provider>-standalone-cp  # Only template changes
  config:
    # Provider-agnostic configuration
    controlPlaneNumber: 3
    workersNumber: 5
```

**2. Standard Kubernetes Distribution**
- All clusters use k0s by default
- Consistent Kubernetes version across providers
- Same CNI (Cilium) and CSI drivers where possible

**3. Centralized Service Deployment (KSM)**
- Deploy services uniformly across clusters
- Single source of truth for configurations
- GitOps-driven consistency

### Network Connectivity Between Clusters

**Options for Cross-Cluster Communication:**

| Approach | Complexity | Use Case |
|----------|------------|----------|
| VPN/VPC Peering | Low | Simple cross-region |
| Service Mesh (Istio) | Medium | Service-to-service |
| Submariner | Medium | Multi-cluster networking |
| Cilium Cluster Mesh | Low | Native Cilium clusters |

**Example: Cilium Cluster Mesh**
```yaml
# Enable cluster mesh on each cluster
apiVersion: cilium.io/v2alpha1
kind: CiliumClusterConfig
metadata:
  name: cluster-mesh-config
spec:
  clusterMesh:
    enabled: true
    service:
      type: LoadBalancer
```

### Cost Optimization

**Multi-Provider Cost Strategies:**

1. **Spot/Preemptible Instances:** Use for stateless workloads
2. **Reserved Capacity:** Long-running control planes
3. **Provider-Specific Pricing:** Choose based on workload characteristics
4. **Data Transfer:** Minimize cross-cloud traffic

**Cost Visibility with KOF:**
- Per-cluster cost attribution
- Per-tenant billing
- Resource utilization reports
- Rightsizing recommendations
