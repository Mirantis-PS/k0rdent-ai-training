### Key Custom Resource Definitions (CRDs)

#### Management

The `Management` CRD is the central configuration object for k0rdent. It defines which providers are enabled, core settings, and release configurations.

```yaml
apiVersion: k0rdent.mirantis.com/v1beta1
kind: Management
metadata:
  name: kcm
  namespace: kcm-system
spec:
  release: kcm-0-1-0  # k0rdent release version
  core:
    kcm:
      config:
        # Core controller settings
        watchNamespace: ""  # Empty = watch all namespaces
    capi:
      config:
        # Cluster API settings
  providers:
    - name: aws
      config:
        # AWS provider configuration
    - name: azure
      config:
        # Azure provider configuration
    # Additional providers: gcp, vsphere, openstack, metal3, etc.
```

**Key Fields:**
- `spec.release` - k0rdent release bundle to use
- `spec.core.kcm` - KCM controller settings
- `spec.core.capi` - Cluster API core settings
- `spec.providers` - List of enabled infrastructure providers with their configs

#### ClusterTemplate

Templates define reusable cluster configurations that can be instantiated multiple times.

```yaml
apiVersion: k0rdent.mirantis.com/v1beta1
kind: ClusterTemplate
metadata:
  name: aws-standalone-cp
  namespace: kcm-system
spec:
  helm:
    chartSpec:
      chart: aws-standalone-cp
      version: 0.0.3
      sourceRef:
        kind: HelmRepository
        name: k0rdent-templates
  providers:
    infrastructure: aws
    bootstrap: k0s
    controlPlane: k0s
  capiContracts:
    - infrastructure-v1beta2
    - controlplane-v1beta2
```

**Types of Templates:**
- **Standalone Control Plane:** Single-node cluster for dev/test
- **Highly Available Control Plane:** Multi-node control plane for production
- **Worker-only:** Join workers to existing cluster
- **Hosted Control Plane:** Control plane runs as pods

#### ClusterDeployment

Represents an actual cluster to be provisioned. References a template and provides configuration values.

```yaml
apiVersion: k0rdent.mirantis.com/v1beta1
kind: ClusterDeployment
metadata:
  name: my-workload-cluster
  namespace: my-tenant
spec:
  template: aws-standalone-cp
  credential: aws-creds
  config:
    region: us-east-1
    publicIP: true
    controlPlane:
      instanceType: t3.large
      amiID: ""  # Uses default AMI
    controlPlaneNumber: 1
    workersNumber: 2
    worker:
      instanceType: t3.medium
```

**Lifecycle States:**
| State | Description |
|-------|-------------|
| `Pending` | Waiting for prerequisites (credentials, template) |
| `Provisioning` | Infrastructure being created |
| `Ready` | Cluster is operational |
| `Upgrading` | Cluster version upgrade in progress |
| `Deleting` | Tear-down in progress |
| `Failed` | Error occurred (check status.conditions) |

#### Credential

Stores cloud provider authentication. Credentials reference Kubernetes Secrets containing actual keys.

```yaml
apiVersion: k0rdent.mirantis.com/v1beta1
kind: Credential
metadata:
  name: aws-cluster-identity-cred
  namespace: kcm-system
spec:
  identityRef:
    apiVersion: infrastructure.cluster.x-k8s.io/v1beta2
    kind: AWSClusterStaticIdentity
    name: aws-cluster-identity
    namespace: kcm-system
```

#### ProviderTemplate

ProviderTemplates register infrastructure providers (CAPA, CAPZ, etc.) with k0rdent. They ship pre-installed with k0rdent Enterprise and define which CAPI controllers to deploy.

```yaml
apiVersion: k0rdent.mirantis.com/v1beta1
kind: ProviderTemplate
metadata:
  name: cluster-api-provider-aws
  namespace: kcm-system
spec:
  helm:
    chartSpec:
      chart: cluster-api-provider-aws
      version: 2.7.1
      sourceRef:
        kind: HelmRepository
        name: k0rdent-templates
  capiContracts:
    - infrastructure-v1beta2
```

> **Note:** You rarely need to create ProviderTemplates manually — they ship with k0rdent releases. Custom ProviderTemplates are only needed when integrating a new CAPI provider not included in the default set.

#### ClusterTemplateChain and ServiceTemplateChain

Template chains define upgrade paths between template versions. They control which versions a cluster or service can upgrade to, preventing incompatible jumps.

**ClusterTemplateChain Example:**

```yaml
apiVersion: k0rdent.mirantis.com/v1beta1
kind: ClusterTemplateChain
metadata:
  name: aws
  namespace: kcm-system
spec:
  supportedTemplates:
    - name: aws-standalone-cp-0-0-2
      availableUpgrades:
        - name: aws-standalone-cp-0-0-3
    - name: aws-standalone-cp-0-0-3
```

**ServiceTemplateChain Example:**

```yaml
apiVersion: k0rdent.mirantis.com/v1beta1
kind: ServiceTemplateChain
metadata:
  name: ingress-nginx-chain
  namespace: kcm-system
spec:
  supportedTemplates:
    - name: ingress-nginx-4-11-3
      availableUpgrades:
        - name: ingress-nginx-4-11-5
    - name: ingress-nginx-4-11-5
```

**Key Points:**
- Chains are **immutable** after creation — define upgrade paths carefully
- If no `templateChain` is specified in a deployment, upgrades are not managed
- Both cluster and service upgrades follow the same chain pattern
- The `availableUpgrades` field defines which version(s) a template can upgrade to

### k0smotron

k0smotron is a critical component within KCM that extends Cluster API with k0s-specific functionality. Without k0smotron, k0rdent could not use k0s as its Kubernetes distribution.

**What k0smotron Provides:**

| Capability | Description |
|-----------|-------------|
| **Bootstrap Provider** | Initializes k0s on cluster nodes (replaces kubeadm bootstrap) |
| **Control Plane Provider** | Manages k0s control plane lifecycle and configuration |
| **Hosted Control Plane** | Runs the control plane as pods on the management cluster instead of dedicated VMs |
| **RemoteMachine Provider** | Deploys clusters via SSH to arbitrary Linux servers (edge, bare metal) |

**How k0smotron Fits in the Architecture:**

```
┌────────────────────────────────────────────────────────┐
│                        KCM                              │
│  ┌──────────────────┐  ┌──────────────────────────┐    │
│  │  kcm-controller  │  │    CAPI Controllers      │    │
│  │     manager      │  │  ┌─────────────────────┐ │    │
│  │                  │  │  │ Infrastructure      │ │    │
│  │                  │  │  │ (CAPA, CAPZ, etc.)  │ │    │
│  │                  │  │  ├─────────────────────┤ │    │
│  │                  │  │  │ k0smotron           │ │    │
│  │                  │  │  │ - Bootstrap (k0s)   │ │    │
│  │                  │  │  │ - ControlPlane (k0s)│ │    │
│  │                  │  │  │ - RemoteMachine     │ │    │
│  │                  │  │  └─────────────────────┘ │    │
│  └──────────────────┘  └──────────────────────────┘    │
└────────────────────────────────────────────────────────┘
```

**Hosted Control Planes:**

In a standard deployment, the control plane runs on dedicated VMs in the target infrastructure. With k0smotron's Hosted Control Plane mode, the control plane runs as pods on the management cluster itself:

```
Standard:  Management Cluster ──▶ Control Plane VMs + Worker VMs
Hosted:    Management Cluster (CP pods) ──▶ Worker VMs only
```

**When to use Hosted Control Planes:**
- **Edge deployments** — minimize infrastructure at edge locations
- **Cost savings** — no dedicated control plane VMs needed
- **Fast provisioning** — pods start faster than VMs
- **Trade-off:** Shared failure domain with management cluster; management cluster sizing matters more

**RemoteMachine Provider:**

The RemoteMachine provider enables deploying k0s clusters via SSH to any Linux server — no cloud API needed. This is used for:
- Bare metal servers without BMC/Redfish
- Small-scale edge devices
- Development environments on existing servers

```yaml
# Example: RemoteMachine ClusterDeployment
apiVersion: k0rdent.mirantis.com/v1beta1
kind: ClusterDeployment
metadata:
  name: edge-cluster
  namespace: kcm-system
spec:
  template: remote-cluster-1-0-15
  credential: remote-cred
  config:
    k0smotron:
      service:
        type: LoadBalancer
    machines:
    - address: 10.0.1.10
      user: root
      port: 22
    - address: 10.0.1.11
      user: root
      port: 22
```

> **Note:** RemoteMachine is the only provider where the `Credential` references a Secret directly (containing the SSH key) without an intermediate identity CRD.

## 2. k0rdent State Manager (KSM) - Deep Dive

### Purpose

KSM manages the installation and lifecycle of services deployed to workload clusters. It ensures applications are deployed consistently across your fleet.

### Architecture

```
┌────────────────────────────────────────────────────────┐
│                        KSM                              │
│  ┌──────────────────┐  ┌──────────────────────────┐    │

│  │  - ServiceTemp   │  │  │ Source │ │  Helm   │  │    │
│  │  - MultiCluster  │  │  │  Ctrl  │ │  Ctrl   │  │    │
│  │    Service       │  │  └────────┘ └─────────┘  │    │
│  └──────────────────┘  └──────────────────────────┘    │
│                                                        │
│  ┌──────────────────────────────────────────────────┐  │
│  │             Service Catalog                       │  │
│  │  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌────────┐ │  │
│  │  │Ingress  │ │Monitoring│ │GPU Op  │ │ vLLM   │ │  │
│  │  └─────────┘ └─────────┘ └─────────┘ └────────┘ │  │
│  └──────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────┘
```

### Gateway API & Envoy Gateway

k0rdent Enterprise uses the **Kubernetes Gateway API** to expose the management UI and route traffic to services. Gateway API is the Kubernetes-native successor to the Ingress API, offering a role-oriented model with clearer separation of concerns:

| Resource | Owner | Purpose |
|----------|-------|---------|
| **GatewayClass** | Infrastructure provider | Defines the controller (e.g., Envoy Gateway) |
| **Gateway** | Cluster operator | Configures listeners (ports, protocols, TLS) |
| **HTTPRoute** | Application developer | Routes traffic to backend services |

**Why Gateway API over Ingress?**
- **Role separation** — infrastructure teams manage GatewayClass/Gateway, app teams manage HTTPRoutes
- **Richer routing** — header-based routing, traffic splitting, request mirroring built-in
- **Portable** — same resources work across Envoy Gateway, Istio, Cilium, and other implementations
- **Active standard** — Ingress API is frozen; Gateway API is where Kubernetes networking evolves

**Envoy Gateway** is a CNCF project that implements Gateway API using **Envoy proxy** as the data plane. It provides a simple operator model: install via Helm, create a GatewayClass, and the controller handles the rest — including provisioning cloud LoadBalancers via the cloud controller manager.

In the training lab, Envoy Gateway runs on the management cluster and exposes the k0rdent UI. The same pattern applies to child clusters for workload ingress.

### AWS Cloud Controller Manager (CCM)

When Envoy Gateway creates a `type: LoadBalancer` Service, *something* needs to provision the actual cloud load balancer. That something is the **AWS Cloud Controller Manager (CCM)** — the bridge between Kubernetes Service abstractions and AWS infrastructure.

#### How CCM Provisions a LoadBalancer

```
1. Envoy Gateway controller sees the Gateway resource
   └─▶ Creates a LoadBalancer Service in envoy-gateway-system

2. CCM watches for LoadBalancer Services
   └─▶ Detects the new Service

3. CCM calls AWS APIs:
   ├─ CreateLoadBalancer (Classic ELB in public subnets)
   ├─ CreateListener (port 80 → NodePort on the instance)
   ├─ RegisterInstances (adds EC2 instance as target)
   └─ Updates Service.status.loadBalancer.ingress with ELB DNS

4. Envoy Gateway reads the Service status
   └─▶ Copies the address to Gateway.status.addresses
```

#### How CCM Finds Resources

CCM uses **AWS tags** to discover which cloud resources belong to its cluster:

| Resource | Required Tag | Purpose |
|----------|-------------|---------|
| **EC2 Instance** | `kubernetes.io/cluster/<cluster-name>=owned` | Identifies which instances belong to the cluster |
| **Public Subnets** | `kubernetes.io/role/elb=1` | Tells CCM where to place internet-facing load balancers |
| **Private Subnets** | `kubernetes.io/role/internal-elb=1` | Tells CCM where to place internal load balancers |

Without these tags, CCM cannot determine the **ClusterID** (it refuses to start) and cannot discover **subnets** for LoadBalancer placement.

CCM also needs to map Kubernetes nodes to EC2 instances. It does this via the **providerID** on each node (`aws:///az/instance-id`), which allows CCM to call `RegisterInstances` with the correct EC2 instance ID.

#### CCM in the Training Lab

In the training lab, CCM runs as a DaemonSet in `kube-system` and uses the **EC2 instance profile** for AWS API credentials — no secrets needed. The Terraform module handles all the tagging automatically.

```bash
# Verify CCM is running
kubectl get pods -n kube-system | grep cloud

# Check what LoadBalancers CCM has provisioned
kubectl get svc -A --field-selector spec.type=LoadBalancer

# View the node's providerID (set during init from IMDS)
kubectl get nodes -o jsonpath='{.items[0].spec.providerID}'
```

> **Troubleshooting tip:** If a LoadBalancer Service stays in `<pending>`, check: (1) CCM pod is running, (2) EC2 instance has the `kubernetes.io/cluster/<name>` tag, (3) subnets have the `kubernetes.io/role/elb` tag, (4) the node has a providerID set. These are the four points in the chain where things can break.

### Key Concepts

#### ServiceTemplate

Defines a service that can be deployed to workload clusters. Wraps a Helm chart with deployment configuration.

```yaml
apiVersion: k0rdent.mirantis.com/v1beta1
kind: ServiceTemplate
metadata:
  name: ingress-nginx
  namespace: kcm-system
spec:
  helm:
    chartSpec:
      chart: ingress-nginx
      version: 4.9.0
      sourceRef:
        kind: HelmRepository
        name: ingress-nginx
        namespace: kcm-system
  providers:
    - infrastructure-aws
    - infrastructure-azure
```

#### MultiClusterService

Deploys services to clusters matching a label selector. This is the primary mechanism for fleet-wide service deployment.

```yaml
apiVersion: k0rdent.mirantis.com/v1beta1
kind: MultiClusterService
metadata:
  name: monitoring-stack
  namespace: kcm-system
spec:
  clusterSelector:
    matchLabels:
      environment: production
  serviceSpec:
    services:
    - template: kube-prometheus-stack
      name: monitoring
      namespace: monitoring
      values: |
        prometheus:
          retention: 30d
        grafana:
          enabled: true
    priority: 100
```

> **Note:** Services can also be deployed to a single cluster directly via `ClusterDeployment.spec.serviceSpec`. MultiClusterService is for fleet-wide deployment across clusters matching labels.

### Integration with Helm

KSM uses Flux's Helm Controller under the hood:
1. ServiceTemplates define which Helm chart to use
2. MultiClusterServices specify target clusters (via label selectors) and service values
3. KSM creates HelmRelease objects on target clusters via Sveltos
4. Flux reconciles the HelmRelease to install/upgrade the chart

### GitOps Model

KSM integrates with Flux for GitOps workflows:
- **HelmRepository:** Sources for Helm charts
- **GitRepository:** Sources for manifests and configurations
- **Kustomization:** Apply kustomize overlays
- **Automatic sync:** Changes in Git trigger deployments

## 3. k0rdent Observability and FinOps (KOF) - Deep Dive

### Purpose

KOF provides monitoring, logging, and cost visibility across the cluster fleet. It aggregates data from all workload clusters into a central view.

### Components

```
┌────────────────────────────────────────────────────────┐
│                        KOF                              │
│                                                        │
│  ┌─────────────────────────────────────────────────┐  │
│  │              Metrics Pipeline                     │  │
│  │  OpenTelemetry ──▶ VictoriaMetrics ──▶ Grafana   │  │
│  └─────────────────────────────────────────────────┘  │
│                                                        │
│  ┌─────────────────────────────────────────────────┐  │
│  │              Logging Pipeline                     │  │
│  │  OpenTelemetry ──▶ VictoriaLogs ──▶ Grafana      │  │
│  └─────────────────────────────────────────────────┘  │
│                                                        │
│  ┌─────────────────────────────────────────────────┐  │
│  │              Tracing Pipeline                      │  │
│  │  OpenTelemetry ──▶ Jaeger ──▶ Grafana            │  │
│  └─────────────────────────────────────────────────┘  │
│                                                        │
│  ┌─────────────────────────────────────────────────┐  │
│  │              Cost Management                      │  │
│  │  OpenCost ──▶ Usage Reports ──▶ Dashboards       │  │
│  └─────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────┘
```

#### Metrics Collection

KOF deploys collectors to workload clusters that forward metrics to the mothership:
- **OpenTelemetry Collector:** Collects and forwards metrics from each cluster
- **VictoriaMetrics (vminsert/vmselect/vmstorage):** Central metrics storage and querying
- **Grafana:** Dashboards for visualization

#### Log Aggregation

Centralized logging for troubleshooting:
- **OpenTelemetry Collector:** Log collector on each cluster
- **VictoriaLogs:** Log storage and indexing
- **Grafana:** Log exploration

#### Distributed Tracing

End-to-end request tracing across services:
- **OpenTelemetry Collector:** Trace collection and forwarding
- **Jaeger:** Trace storage, indexing, and visualization
- **Grafana:** Trace exploration and correlation

#### Cost Management (FinOps)

Cost visibility and optimization:
- **OpenCost:** Kubernetes cost allocation
- **Resource metrics:** CPU, memory, GPU utilization
- **Tenant attribution:** Cost per namespace/team
- **Recommendations:** Rightsizing suggestions

## 4. Component Reference

A k0rdent Enterprise management cluster runs ~45 pods across 5 namespaces. This section describes every component and its role.

### kcm-system — k0rdent Control Plane

The primary namespace. Contains the k0rdent controllers, CAPI providers, Flux, and supporting infrastructure.

#### k0rdent Core

| Component | Pod Prefix | Role |
|-----------|-----------|------|
| **KCM Controller Manager** | `kcm-k0rdent-enterprise-controller-manager` | The main k0rdent controller. Reconciles Management, ClusterDeployment, MultiClusterService, and template CRDs. Orchestrates the entire platform. |
| **k0rdent UI** | `kcm-k0rdent-ui` | Web dashboard for managing clusters, templates, and credentials. Exposed externally via Envoy Gateway. |
| **KCM RBAC Manager** | `kcm-rbac-manager` | Manages RBAC roles and bindings for multi-tenant access. Translates k0rdent AccessManagement CRDs into Kubernetes RBAC. |
| **KCM Datasource Controller** | `kcm-datasource-controller-manager` | Manages data source integrations. Feeds external data into k0rdent for decision-making (e.g., cluster health, cost data). |
| **KCM Regional Telemetry** | `kcm-regional-telemetry` | Collects and forwards telemetry data from the management cluster and managed clusters. |
| **Cluster API Operator** | `kcm-cluster-api-operator` | Manages the lifecycle of CAPI providers. Installs, upgrades, and configures provider controllers based on the Management object. |
| **Velero** | `velero` | Backup and disaster recovery. Takes scheduled backups of k0rdent CRDs and etcd state to S3. |

#### Cluster API (CAPI) Controllers

These controllers implement the Kubernetes Cluster API. Each provider controller knows how to provision infrastructure on a specific cloud or platform.

| Component | Pod Prefix | Role |
|-----------|-----------|------|
| **CAPI Core** | `capi-controller-manager` | The Cluster API core controller. Manages the lifecycle of Cluster, Machine, MachineDeployment objects. Provider-agnostic orchestration. |
| **CAPA (AWS)** | `capa-controller-manager` | AWS infrastructure provider. Creates VPCs, EC2 instances, ELBs, security groups for AWS-based clusters. |
| **CAPZ (Azure)** | `capz-controller-manager` | Azure infrastructure provider. Provisions AKS clusters, VMs, VNets for Azure-based clusters. |
| **CAPG (GCP)** | `capg-controller-manager` | GCP infrastructure provider. Manages GKE clusters, Compute instances, VPCs for GCP-based clusters. |
| **CAPV (vSphere)** | `capv-controller-manager` | vSphere infrastructure provider. Creates VMs on vCenter for on-premises clusters. |
| **CAPO (OpenStack)** | `capo-controller-manager` | OpenStack infrastructure provider. Provisions instances and networks on OpenStack clouds. |
| **CAPD (Docker)** | `capd-controller-manager` | Docker infrastructure provider. Creates clusters using Docker containers (development/testing only). |
| **Azure Service Operator** | `azureserviceoperator-controller-manager` | Manages Azure resources (resource groups, identities) that CAPZ depends on. |
| **IPAM In-Cluster** | `capi-ipam-in-cluster-controller-manager` | Assigns IP addresses to cluster nodes from in-cluster IP pools. Used for static IP environments. |
| **IPAM Infoblox** | `capi-ipam-infoblox-controller-manager` | Integrates with Infoblox IPAM for enterprise IP address management. |

#### k0smotron Controllers

k0smotron enables **hosted control planes** — running workload cluster control planes as pods on the management cluster.

| Component | Pod Prefix | Role |
|-----------|-----------|------|
| **Bootstrap Controller** | `k0smotron-controller-manager-bootstrap` | Generates bootstrap tokens and cloud-init configurations for new worker nodes joining a k0smotron-managed cluster. |
| **Control Plane Controller** | `k0smotron-controller-manager-control-plane` | Manages the lifecycle of hosted control plane pods. Creates/scales/upgrades the k0s control plane running as a StatefulSet. |
| **Infrastructure Controller** | `k0smotron-controller-manager-infrastructure` | Handles the RemoteMachine provider — connects bare-metal or pre-existing machines to k0smotron clusters via SSH. |

#### Flux CD (GitOps Engine)

k0rdent uses Flux internally for Helm chart management and reconciliation.

| Component | Pod Prefix | Role |
|-----------|-----------|------|
| **Helm Controller** | `helm-controller` | Reconciles HelmRelease objects. Installs, upgrades, and rolls back Helm charts based on desired state. Used by KSM to deploy services to clusters. |
| **Source Controller** | `source-controller` | Fetches Helm charts and OCI artifacts from registries. Provides the chart content that Helm Controller installs. |

#### Certificate Management

| Component | Pod Prefix | Role |
|-----------|-----------|------|
| **cert-manager** | `kcm-cert-manager` | Issues and renews TLS certificates for webhook endpoints and internal communication. All CAPI providers and k0rdent controllers depend on it. |
| **CA Injector** | `kcm-cert-manager-cainjector` | Injects CA certificates into webhook configurations so the API server trusts the webhooks. |
| **Webhook** | `kcm-cert-manager-webhook` | Validates and mutates cert-manager CRDs (Certificate, Issuer, etc.). |

### projectsveltos — Service Distribution Engine

Sveltos is the engine behind k0rdent's MultiClusterService. It distributes Helm charts, YAML manifests, and policies to managed clusters based on label selectors.

| Component | Pod Prefix | Role |
|-----------|-----------|------|
| **Addon Controller** | `addon-controller` | The core Sveltos controller. Watches ClusterProfile/Profile CRDs and deploys addons (Helm charts, raw YAML) to matching clusters. This is what makes MultiClusterService work. |
| **Classifier Manager** | `classifier-manager` | Classifies clusters by evaluating rules against cluster properties (version, labels, resources). Enables dynamic cluster grouping for targeted deployments. |
| **Event Manager** | `event-manager` | Watches for events in managed clusters and triggers actions (e.g., auto-remediation, scaling). Implements EventSource and EventTrigger CRDs. |
| **Access Manager** | `access-manager` | Manages RBAC distribution to managed clusters. Ensures consistent access policies across the fleet. |
| **SC Manager** | `sc-manager` | Manages SveltosCluster resources — the Sveltos representation of each managed cluster. Tracks cluster connectivity and health. |
| **HC Manager** | `hc-manager` | Health Check manager. Evaluates HealthCheck and ClusterHealthCheck CRDs against managed clusters and reports results. |
| **Shard Controller** | `shard-controller` | Distributes workload across multiple Sveltos controller replicas for large-scale fleets. Enables horizontal scaling of the management plane. |
| **Sveltos Agent** | `sveltos-agent-manager` | Runs on the management cluster to collect status from managed clusters and report back to Sveltos controllers. |
| **Tech Support Controller** | `techsupport-controller` | Collects diagnostic information from managed clusters on demand. Creates support bundles for troubleshooting. |
| **MCP Server** | `mcp-server` | Model Context Protocol server. Provides an API for AI assistants and automation tools to interact with Sveltos. |

### orc-system — OpenStack Resource Controller

| Component | Pod Prefix | Role |
|-----------|-----------|------|
| **ORC Controller Manager** | `orc-controller-manager` | Manages OpenStack resources as Kubernetes CRDs. Used by CAPO to provision and track OpenStack infrastructure (networks, subnets, routers, images). |

### envoy-gateway-system — Ingress Layer

| Component | Pod Prefix | Role |
|-----------|-----------|------|

### Tenant Namespaces

Each tenant gets isolated namespaces for their resources:

```

│   ├── production-cluster
│   └── staging-cluster
```

**Isolation Model:**
- Tenants can only see their own namespaces
- ClusterDeployments in tenant namespace use tenant credentials
- RBAC restricts access to tenant resources
- Quotas limit resource consumption

## 5. Controller Pattern

### How Controllers Work

k0rdent uses the Kubernetes controller pattern (also called the operator pattern):

```
┌─────────────┐     ┌──────────────┐     ┌─────────────────┐
│  User       │     │  API Server  │     │   Controller    │
│  applies    │────▶│  stores      │────▶│   watches for   │
│  manifest   │     │  object      │     │   changes       │
└─────────────┘     └──────────────┘     └────────┬────────┘
                                                  │
                                                  ▼
                                         ┌─────────────────┐
                                         │   Reconcile()   │
                                         │   function      │
                                         └────────┬────────┘
                                                  │
                                                  ▼
                                         ┌─────────────────┐
                                         │ Infrastructure  │
                                         │ is provisioned  │
                                         └─────────────────┘
```

### Reconciliation Loop

The controller continuously ensures actual state matches desired state:

1. **Watch:** Monitor CRDs for create/update/delete events
2. **Compare:** Calculate diff between desired and actual state
3. **Act:** Make changes to bring actual state to desired
4. **Status:** Update CRD status with current state
5. **Requeue:** Schedule next reconciliation

**Example: ClusterDeployment Reconciliation**

```
ClusterDeployment created
         │
         ▼
┌────────────────────┐
│ Check prerequisites│ ─── Credential exists?
└────────┬───────────┘     Template exists?
         │
         ▼
┌────────────────────┐
│ Create CAPI objects│ ─── Cluster, Machines,
└────────┬───────────┘     MachineDeployments
         │
         ▼
┌────────────────────┐
│ Wait for provision │ ─── Poll infrastructure
└────────┬───────────┘     provider status
         │
         ▼
┌────────────────────┐
│ Update status      │ ─── Set Ready condition
└────────────────────┘
```

## Knowledge Check

1. What is the purpose of the `Management` CRD?
2. How does a `ClusterTemplate` differ from a `ClusterDeployment`?
3. What namespace contains the k0rdent controllers?
4. Explain the reconciliation loop pattern.
5. How are credentials stored and referenced?
6. What is the role of Flux in KSM?
7. How does KOF collect metrics from workload clusters?

<details>
<summary><strong>Answer Key</strong> (click to expand)</summary>

1. The `Management` CRD is the central configuration object for k0rdent. It defines which providers are enabled, the release version, and core settings for KCM and CAPI.
2. A **ClusterTemplate** is a reusable blueprint (Helm chart reference + provider requirements). A **ClusterDeployment** is an instance that references a template and provides concrete configuration values (region, instance types, node counts) to provision an actual cluster.
3. **kcm-system** -- all k0rdent controllers, CAPI controllers, and provider controllers run here.
4. Watch for CRD changes -> Compare desired vs actual state -> Act to reconcile differences -> Update CRD status -> Requeue for next check. This continuous loop ensures the cluster always converges toward the declared desired state.
5. Credentials use a three-layer model: a Kubernetes **Secret** (holds actual keys) -> a provider-specific identity CRD like **AWSClusterStaticIdentity** (references the secret) -> a k0rdent **Credential** CRD (references the identity, used by ClusterDeployments).
6. Flux provides the **Helm Controller** and **Source Controller** that KSM uses under the hood. KSM creates HelmRelease objects; Flux reconciles them to install/upgrade charts on target clusters.
7. KOF deploys **OpenTelemetry Collectors** to workload clusters via MultiClusterService. These collectors forward metrics to **VictoriaMetrics**, logs to **VictoriaLogs**, and traces to **Jaeger** on the management cluster (mothership). **Grafana** provides the visualization layer.

</details>
