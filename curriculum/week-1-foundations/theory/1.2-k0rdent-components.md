## 1. k0rdent Cluster Manager (KCM) - Deep Dive

### Architecture

```
┌────────────────────────────────────────────────────────┐
│                        KCM                              │
│  ┌──────────────────┐  ┌──────────────────────────┐    │
│  │  kcm-controller  │  │    Provider Controllers  │    │
│  │     manager      │  │  ┌─────┐ ┌─────┐ ┌────┐ │    │
│  │                  │  │  │CAPA │ │CAPZ │ │... │ │    │
│  │  - Management    │  │  └─────┘ └─────┘ └────┘ │    │
│  │  - Templates     │  └──────────────────────────┘    │
│  │  - Deployments   │                                  │
│  └──────────────────┘                                  │
│                                                        │
│  ┌──────────────────┐  ┌──────────────────────────┐    │
│  │   cert-manager   │  │      Flux Controllers    │    │
│  │                  │  │   (GitOps integration)   │    │
│  └──────────────────┘  └──────────────────────────┘    │
└────────────────────────────────────────────────────────┘
```

### Key Custom Resource Definitions (CRDs)

#### Management

The `Management` CRD is the central configuration object for k0rdent. It defines which providers are enabled, core settings, and release configurations.

```yaml
apiVersion: k0rdent.mirantis.com/v1beta1
kind: Management
metadata:
  name: kcm
  namespace: kcm-system
spec:
  release: kcm-0-1-0  # k0rdent release version
  core:
    kcm:
      config:
        # Core controller settings
        watchNamespace: ""  # Empty = watch all namespaces
    capi:
      config:
        # Cluster API settings
  providers:
    - name: aws
      config:
        # AWS provider configuration
    - name: azure
      config:
        # Azure provider configuration
```

**Key Fields:**
- `spec.release` - k0rdent release bundle to use
- `spec.core.kcm` - KCM controller settings
- `spec.core.capi` - Cluster API core settings
- `spec.providers` - List of enabled infrastructure providers with their configs

#### ClusterTemplate

Templates define reusable cluster configurations that can be instantiated multiple times.

```yaml
apiVersion: k0rdent.mirantis.com/v1beta1
kind: ClusterTemplate
metadata:
  name: aws-standalone-cp
  namespace: kcm-system
spec:
  helm:
    chartSpec:
      chart: aws-standalone-cp
      version: 0.0.3
      sourceRef:
        kind: HelmRepository
        name: k0rdent-templates
  providers:
    infrastructure: aws
    bootstrap: k0s
    controlPlane: k0s
  capiContracts:
    - infrastructure-v1beta2
    - controlplane-v1beta2
```

**Types of Templates:**
- **Standalone Control Plane:** Single-node cluster for dev/test
- **Highly Available Control Plane:** Multi-node control plane for production
- **Worker-only:** Join workers to existing cluster
- **Hosted Control Plane:** Control plane runs as pods

#### ClusterDeployment

Represents an actual cluster to be provisioned. References a template and provides configuration values.

```yaml
apiVersion: k0rdent.mirantis.com/v1beta1
kind: ClusterDeployment
metadata:
  name: my-workload-cluster
  namespace: my-tenant
spec:
  template: aws-standalone-cp
  credential: aws-creds
  config:
    region: us-east-1
    publicIP: true
    controlPlane:
      instanceType: t3.large
      amiID: ""  # Uses default AMI
    controlPlaneNumber: 1
    workersNumber: 2
    worker:
      instanceType: t3.medium
```

**Lifecycle States:**
| State | Description |
|-------|-------------|
| `Pending` | Waiting for prerequisites (credentials, template) |
| `Provisioning` | Infrastructure being created |
| `Ready` | Cluster is operational |
| `Upgrading` | Cluster version upgrade in progress |
| `Deleting` | Tear-down in progress |
| `Failed` | Error occurred (check status.conditions) |

#### Credential

Stores cloud provider authentication. Credentials reference Kubernetes Secrets containing actual keys.

```yaml
apiVersion: k0rdent.mirantis.com/v1beta1
kind: Credential
metadata:
  name: aws-creds
  namespace: kcm-system
spec:
  description: "AWS credentials for production"
  identityRef:
    apiVersion: infrastructure.cluster.x-k8s.io/v1beta2
    kind: AWSClusterStaticIdentity
    name: aws-cluster-identity
```

## 2. k0rdent State Manager (KSM) - Deep Dive

### Purpose

KSM manages the installation and lifecycle of services deployed to workload clusters. It ensures applications are deployed consistently across your fleet.

### Architecture

```
┌────────────────────────────────────────────────────────┐
│                        KSM                              │
│  ┌──────────────────┐  ┌──────────────────────────┐    │
│  │  ksm-controller  │  │    Flux Controllers       │    │
│  │                  │  │  ┌────────┐ ┌─────────┐  │    │
│  │  - ServiceTemp   │  │  │ Source │ │  Helm   │  │    │
│  │  - ServiceDeploy │  │  │  Ctrl  │ │  Ctrl   │  │    │
│  │  - MultiCluster  │  │  └────────┘ └─────────┘  │    │
│  └──────────────────┘  └──────────────────────────┘    │
│                                                        │
│  ┌──────────────────────────────────────────────────┐  │
│  │             Service Catalog                       │  │
│  │  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌────────┐ │  │
│  │  │Ingress  │ │Monitoring│ │GPU Op  │ │ vLLM   │ │  │
│  │  └─────────┘ └─────────┘ └─────────┘ └────────┘ │  │
│  └──────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────┘
```

### Key Concepts

#### ServiceTemplate

Defines a service that can be deployed to workload clusters. Wraps a Helm chart with deployment configuration.

```yaml
apiVersion: k0rdent.mirantis.com/v1beta1
kind: ServiceTemplate
metadata:
  name: ingress-nginx
  namespace: kcm-system
spec:
  helm:
    chartSpec:
      chart: ingress-nginx
      version: 4.9.0
      sourceRef:
        kind: HelmRepository
        name: ingress-nginx
        namespace: kcm-system
  providers:
    - infrastructure-aws
    - infrastructure-azure
```

#### ServiceDeployment

Deploys a service to one or more clusters.

```yaml
apiVersion: k0rdent.mirantis.com/v1beta1
kind: ServiceDeployment
metadata:
  name: monitoring-stack
  namespace: my-tenant
spec:
  template: kube-prometheus-stack
  clusterSelector:
    matchLabels:
      environment: production
  config:
    prometheus:
      retention: 30d
    grafana:
      enabled: true
```

### Integration with Helm

KSM uses Flux's Helm Controller under the hood:
1. ServiceTemplates define which Helm chart to use
2. ServiceDeployments specify values and target clusters
3. KSM creates HelmRelease objects on target clusters
4. Flux reconciles the HelmRelease to install/upgrade the chart

### GitOps Model

KSM integrates with Flux for GitOps workflows:
- **HelmRepository:** Sources for Helm charts
- **GitRepository:** Sources for manifests and configurations
- **Kustomization:** Apply kustomize overlays
- **Automatic sync:** Changes in Git trigger deployments

## 3. k0rdent Observability and FinOps (KOF) - Deep Dive

### Purpose

KOF provides monitoring, logging, and cost visibility across the cluster fleet. It aggregates data from all workload clusters into a central view.

### Components

```
┌────────────────────────────────────────────────────────┐
│                        KOF                              │
│                                                        │
│  ┌─────────────────────────────────────────────────┐  │
│  │              Metrics Pipeline                     │  │
│  │  OpenTelemetry ──▶ VictoriaMetrics ──▶ Grafana   │  │
│  └─────────────────────────────────────────────────┘  │
│                                                        │
│  ┌─────────────────────────────────────────────────┐  │
│  │              Logging Pipeline                     │  │
│  │  OpenTelemetry ──▶ VictoriaLogs ──▶ Grafana      │  │
│  └─────────────────────────────────────────────────┘  │
│                                                        │
│  ┌─────────────────────────────────────────────────┐  │
│  │              Tracing Pipeline                      │  │
│  │  OpenTelemetry ──▶ Jaeger ──▶ Grafana            │  │
│  └─────────────────────────────────────────────────┘  │
│                                                        │
│  ┌─────────────────────────────────────────────────┐  │
│  │              Cost Management                      │  │
│  │  OpenCost ──▶ Usage Reports ──▶ Dashboards       │  │
│  └─────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────┘
```

#### Metrics Collection

KOF deploys collectors to workload clusters that forward metrics to the mothership:
- **OpenTelemetry Collector:** Collects and forwards metrics from each cluster
- **VictoriaMetrics (vminsert/vmselect/vmstorage):** Central metrics storage and querying
- **Grafana:** Dashboards for visualization

#### Log Aggregation

Centralized logging for troubleshooting:
- **OpenTelemetry Collector:** Log collector on each cluster
- **VictoriaLogs:** Log storage and indexing
- **Grafana:** Log exploration

#### Distributed Tracing

End-to-end request tracing across services:
- **OpenTelemetry Collector:** Trace collection and forwarding
- **Jaeger:** Trace storage, indexing, and visualization
- **Grafana:** Trace exploration and correlation

#### Cost Management (FinOps)

Cost visibility and optimization:
- **OpenCost:** Kubernetes cost allocation
- **Resource metrics:** CPU, memory, GPU utilization
- **Tenant attribution:** Cost per namespace/team
- **Recommendations:** Rightsizing suggestions

## 4. Namespace Structure

### kcm-system Namespace

The primary namespace for k0rdent components:

```
kcm-system/
├── Deployments
│   ├── kcm-controller-manager    # Main KCM controller
│   ├── capi-controller-manager   # Cluster API core
│   ├── capa-controller-manager   # AWS provider
│   ├── cert-manager              # Certificate management
│   └── k0rdent-ui                # Web interface
├── Secrets
│   ├── aws-credentials           # Cloud provider creds
│   ├── azure-credentials
│   └── tls-certificates          # TLS for webhooks
├── ConfigMaps
│   └── kcm-config                # Configuration data
└── CRDs (cluster-scoped)
    ├── Management
    ├── ClusterTemplates
    ├── ServiceTemplates
    └── Credentials
```

### Tenant Namespaces

Each tenant gets isolated namespaces for their resources:

```
tenant-acme/                      # Tenant namespace
├── ClusterDeployments            # Tenant's clusters
│   ├── production-cluster
│   └── staging-cluster
├── ServiceDeployments            # Tenant's services
├── Secrets                       # Tenant credentials
└── ResourceQuota                 # Tenant limits
```

**Isolation Model:**
- Tenants can only see their own namespaces
- ClusterDeployments in tenant namespace use tenant credentials
- RBAC restricts access to tenant resources
- Quotas limit resource consumption

## 5. Controller Pattern

### How Controllers Work

k0rdent uses the Kubernetes controller pattern (also called the operator pattern):

```
┌─────────────┐     ┌──────────────┐     ┌─────────────────┐
│  User       │     │  API Server  │     │   Controller    │
│  applies    │────▶│  stores      │────▶│   watches for   │
│  manifest   │     │  object      │     │   changes       │
└─────────────┘     └──────────────┘     └────────┬────────┘
                                                  │
                                                  ▼
                                         ┌─────────────────┐
                                         │   Reconcile()   │
                                         │   function      │
                                         └────────┬────────┘
                                                  │
                                                  ▼
                                         ┌─────────────────┐
                                         │ Infrastructure  │
                                         │ is provisioned  │
                                         └─────────────────┘
```

### Reconciliation Loop

The controller continuously ensures actual state matches desired state:

1. **Watch:** Monitor CRDs for create/update/delete events
2. **Compare:** Calculate diff between desired and actual state
3. **Act:** Make changes to bring actual state to desired
4. **Status:** Update CRD status with current state
5. **Requeue:** Schedule next reconciliation

**Example: ClusterDeployment Reconciliation**

```
ClusterDeployment created
         │
         ▼
┌────────────────────┐
│ Check prerequisites│ ─── Credential exists?
└────────┬───────────┘     Template exists?
         │
         ▼
┌────────────────────┐
│ Create CAPI objects│ ─── Cluster, Machines,
└────────┬───────────┘     MachineDeployments
         │
         ▼
┌────────────────────┐
│ Wait for provision │ ─── Poll infrastructure
└────────┬───────────┘     provider status
         │
         ▼
┌────────────────────┐
│ Update status      │ ─── Set Ready condition
└────────────────────┘
```

## 6. Hands-on Exploration Commands

Use these commands to explore the components in your lab environment:

```bash
# List all k0rdent CRDs
kubectl get crds | grep k0rdent.mirantis.com

# Describe the Management object
kubectl describe management -n kcm-system

# View controller logs
kubectl logs -n kcm-system -l app.kubernetes.io/name=kcm -f

# List all cluster templates
kubectl get clustertemplates -A -o wide

# List all service templates
kubectl get servicetemplates -A -o wide

# Check provider status
kubectl get providers -n kcm-system

# View cluster deployments
kubectl get clusterdeployments -A

# Check a specific cluster's status
kubectl describe clusterdeployment <name> -n <namespace>
```
