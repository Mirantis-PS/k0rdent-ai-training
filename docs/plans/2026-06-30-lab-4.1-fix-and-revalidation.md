## TL;DR

The hosted-CP crashloop the 2026-05-06 report flagged as "awaits a template
revision" is a **fixed k0s bug**. Pinning the hosted CP's k0s to a fixed,
registry-available build makes the control plane come up cleanly — **validated
live**: all 3 CP replicas + 3 etcd `Running`, no crashloop. A second, unrelated
issue (CAPA DHCP panic) blocked the *worker* join in this validation run only
because it used a non-standard identity; the lab's documented credential path is
doc-verified to avoid it.

## 1. Root cause of the CP crashloop — CONFIRMED

**k0s issue [#7832](https://github.com/k0sproject/k0s/issues/7832):** the helm
`ExtensionsReconciler` polls for the `charts.helm.k0sproject.io` CRD with a hard
cap of 10 attempts (avast/retry-go default) and fatally exits before the async
CRD applier wins the race. Deterministic in single-pod k0smotron CPs → only
hosted CPs hit it; etcd is unaffected. Fixed by k0s
[PR #7217](https://github.com/k0sproject/k0s/pull/7217), first in
**v1.33.9 / v1.34.5 / v1.35.2** (never the EOL 1.32 line).

**Live confirmation:** Enterprise 1.3.1 ships `aws-hosted-cp-1-0-29` →
`.status.version: v1.35.1+k0s.1` (one patch *before* the fix). The stock hosted
CP reproduces the crashloop.

## 2. The fix — VALIDATED LIVE

Pin the hosted CP's k0s to **`v1.35.4+k0s.0`**:
- It contains the #7217 fix (≥ 1.35.2), **and**
- it is present in `registry.mirantis.com/k0rdent-enterprise/k0sproject/k0s`
  (verified via the node's containerd: only `v1.35.1-k0s.1` and `v1.35.4-k0s.0`
  exist for the 1.35 line — **the upstream-minimal `v1.35.2` is NOT in the
  Enterprise registry**, so pinning it yields `ErrImagePull NotFound`).

Two ways to apply it (both set `K0smotronControlPlane.spec.version`):
- **Inline (validated):** `ClusterDeployment.spec.config.k0s.version: v1.35.4+k0s.0`.
  Works because `spec.config` is `x-kubernetes-preserve-unknown-fields` and is
  rendered as the chart's values. One line; what this run used.
- **Forked ClusterTemplate (supported/robust):** copy the `aws-hosted-cp` chart,
  set `k0s.version`, bump chart version, republish, register. Turnkey helper:
  `lab-infrastructure/scripts/lab-4.1-fork-hosted-cp-template.sh`. (Generalized
  in Lab 4.8.)

**Result (live):**
```
kmc-managed-cluster-02-hosted-0/1/2        1/1  Running   (k0s v1.35.4-k0s.0)
kmc-managed-cluster-02-hosted-etcd-0/1/2   1/1  Running
K0smotronControlPlane ... version=v1.35.4-k0s.0   HelmReleaseReady=True
```
No `helm CRD` crashloop. CP LoadBalancer/konnectivity endpoint provisioned. The
control plane — the lab's subject — is fully operational.

## 3. Second issue found: CAPA DHCP panic blocks worker join (not the lab's path)

With the CP healthy, the worker EC2 launched but never registered; the
`ClusterDeployment` hung at `WorkersAvailable`. Cause: **CAPA v2.10.0 nil-panics
in `GetDHCPOptionSetDomainName` (`instances.go:1168`)** when its AWS identity is
denied `ec2:DescribeDhcpOptions` while reading the VPC's DHCP option set.

- **Trigger in this run only:** validation used an `AWSClusterControllerIdentity`
  (the mgmt node instance profile). The terraform IAM module
  (`terraform/modules/iam/main.tf`) granted `ec2:DescribeVpcs` but **not**
  `ec2:DescribeDhcpOptions` — an incomplete hand-rolled policy. → **Fixed in the
  module** (added `DescribeDhcpOptions`).
- **The lab's documented path is unaffected** (doc-verified, per the
  "verify against k0rdent docs" rule): the lab uses an `AWSClusterStaticIdentity`
  whose credentials come from `clusterawsadm bootstrap iam`
  (docs.mirantis.com/k0rdent-enterprise → prepare-mgmt-cluster/aws). The live
  `controllers.cluster-api-provider-aws.sigs.k8s.io` policy on the account
  **includes `ec2:DescribeDhcpOptions`** — so a student following the lab has the
  permission and the worker joins.

## 4. Doc verification (per "always verify with k0rdent docs")

Confirmed against docs.mirantis.com/k0rdent-enterprise:
- AWS credential setup = Secret (`AccessKeyID`/`SecretAccessKey`, label
  `k0rdent.mirantis.com/component: kcm`, ns `kcm-system`) + `AWSClusterStaticIdentity`
  (`secretRef`, `allowedNamespaces: {}`) + k0rdent `Credential`. Matches the lab.
- IAM = `clusterawsadm bootstrap iam create-cloudformation-stack`; its
  `controllers` policy includes `ec2:DescribeDhcpOptions` (live-verified).

## 5. Live end-to-end result — CONFIRMED ✅

After applying all three fixes (k0s pin + `DescribeDhcpOptions` + Ubuntu worker
AMI), the cluster reached **`Ready=True` in ~5 min**:
- CP: 6/6 pods Running (3 CP + 3 etcd) at k0s `v1.35.4`, no crashloop.
- Worker **joined and `Ready`**: `...-md-gcscr-plnh9`, **Ubuntu 22.04**, `v1.35.4+k0s`.
- Smoke test: 2 workload pods Running on the worker.
- **0 dedicated CP EC2** (architectural promise holds); CP footprint on mgmt
  cluster ≈ **1.4 GiB / ~2 cores** (3 CP ~1.17 GiB + 3 etcd ~0.23 GiB).

### Third issue found + fixed: worker stuck on Amazon Linux 2
With the CP healthy and DHCP perm granted, the worker EC2 ran but never joined
(no node, no CSR, konnectivity "No agent available"; AL2 cloud-init finished in
17s without installing k0s). The chart defaults the worker AMI to **Amazon
Linux 2**, on which the k0smotron worker bootstrap does not execute. **Fix: set
`config.amiID` to Ubuntu 22.04** (eu-west-1 `ami-0dbc125eb45c6bfb0`). Note: amiID
is **immutable post-creation** (the chart reuses a fixed `AWSMachineTemplate`
name; an in-place `kubectl patch` is rejected) — it must be set in the initial
ClusterDeployment. With Ubuntu, the worker joined in ~2 min. Added to the lab.
