## 🚨 Known Traps (Read Before Executing)

These failure modes were discovered empirically during the Lab 5.1 validation session. Expect them to recur in subsequent labs; apply the fixes preemptively where obvious.

### TRAP 1: STS credential expiration during long labs

**Symptom:** CAPA controller logs emit `RequestExpired` / `AuthFailure` (sometimes labeled "Probable clock skew error"). Cluster provisioning stalls. Deletion stalls in `Terminating but pending` for >5 minutes.

**Root cause:** AWS SSO session tokens typically expire after 1-12 hours. CAPA reads credentials into env vars at process start from `Secret/aws-cluster-identity-secret`. When the STS token expires, CAPA silently cannot call AWS APIs. k0rdent's `Credential.status.ready=true` is a shallow check and does NOT flag the expiration.

**Fix:** Run `./lab-infrastructure/scripts/lab-refresh-creds.sh e2e-val` from the local machine with fresh AWS env vars exported. Script rotates the Secret and restarts CAPA. Reconciliation resumes in ~30 seconds.

**Where to apply during Week 5 execution:** Any lab with unattended waits > 1 hour — particularly labs 5.5 (vLLM, 4h), 5.9 (Kubeflow, 3h), 5.10 (MLflow, 2.5h), 5.16 (distributed training, 4.5h).

**Existing lab doc support:** Lab 5.1 already has this note in Pre-Lab Step 2 and Cleanup after commit `af524d3`. Add equivalent notes to the labs listed above if the empirical run hits the trap.

### TRAP 2: ClusterPolicy ambiguity (NVIDIA GPU Operator vs Kyverno)

**Symptom:** `kubectl patch clusterpolicy/cluster-policy ...` fails with `Error from server (NotFound): clusterpolicies.kyverno.io "cluster-policy" not found`.

**Root cause:** Two CRDs share the short name `clusterpolicy`: `clusterpolicies.nvidia.com` (GPU Operator config) and `clusterpolicies.kyverno.io` (Kyverno policy engine). kubectl picks Kyverno's because `kyverno.io` sorts first in API discovery. Kyverno is deployed as a default k0rdent Service on the `aws-standalone-cp-1-0-20` template, so this bug affects every cluster.

**Fix:** Use the fully-qualified name `clusterpolicies.nvidia.com/cluster-policy` in every `kubectl patch` and `kubectl get` command touching GPU Operator config.

**Where to apply:** Any lab that references `clusterpolicy` or `cluster-policy`. Labs 5.3 (KAI Scheduler tuning), 5.4 (Run:AI), 5.11 (NVIDIA FIPS), 5.13 (TensorRT-LLM) are high-risk because they commonly reconfigure GPU Operator.

**Existing lab doc support:** Fixed in Lab 5.1 by commit `ae22d71`. Grep each lab for `clusterpolicy/cluster-policy` and `kubectl get clusterpolicy cluster-policy` before execution; pre-fix if found.

### TRAP 3: KAI Scheduler preemptibility model

**Symptom:** Preemption tests fail with `NonPreemptibleOverQuota` events on the high-priority pod despite correct K8s PriorityClass + `preemptionPolicy: PreemptLowerPriority` settings.

**Root cause:** KAI Scheduler v0.12.10 has its own preemptibility model (`kai.scheduler/preemptibility` label) orthogonal to Kubernetes PriorityClass. Any workload with K8s priority ≥ 100 defaults to **non-preemptible** in KAI unless the label explicitly says otherwise. The Kubernetes `preemptionPolicy` field is ignored by KAI.

**Fix:** Add `kai.scheduler/preemptibility: "preemptible"` to pod-template labels on workloads that should be evictable.

**Where to apply:** Labs 5.3 (KAI Scheduler), 5.4 (Run:AI — same code path), possibly 5.6 (Troubleshooting GPU — preemption scenarios likely).

**Existing lab doc support:** Fixed in Lab 5.1 Task 5 by commit `d359c8c`. Verify via `kai_total_preemption_attempts` metric after the test — should be ≥ 1.

### TRAP 4: Transient states that look like failures

These all auto-heal and should NOT trigger debugging:

| State | When it appears | Duration | Auto-heals? |
|---|---|---|---|
| `NetworkPluginNotReady` on CP Machine | During ClusterDeployment provisioning (Pre-Lab of any lab needing a new cluster) | ~30-60s | Yes, when Calico CNI comes up |
| `ServiceSetEnsureProfileFailed` on CAPI apply | Seconds after `kubectl apply -f <ClusterDeployment>` | milliseconds | Yes, via ProjectSveltos reconcile retry |
| `nvidia-dcgm-exporter` restarts 1-3× | GPU Operator cascade during Pre-Lab Step 4 | ~30s | Yes, after DCGM becomes ready |
| `nvidia.com/gpu.replicas` label shows stale value | After time-slicing ClusterPolicy patch | ~60s | Yes, GPU Feature Discovery refreshes on its cadence |
| kubectl version skew warning (client 1.35 vs server 1.32) | Every `kubectl` invocation on mgmt node | Always | Not a problem — commands work fine |
| `helm install --wait` returns in ~60s for GPU Operator | Pre-Lab Step 4 | Always | Helm exit ≠ GPUs ready; poll `nvidia.com/gpu: N` on node instead |

All five are documented in Lab 5.1 Troubleshooting after commit `e8fe987`.

### TRAP 5: Timing estimates are ~2× pessimistic

Lab-stated durations are safe buffers, not empirical measurements. Actual times observed in Lab 5.1:

| Action | Lab says | Actual |
|---|---|---|
| ClusterDeployment provisioning | ~15 min | ~7 min |
| NVIDIA driver compilation | ~8 min | ~2 min |
| GPU Operator full cascade | implied ~8 min | ~3.5 min |
| Device plugin restart after time-slicing patch | ~60s | ~10s |
| NCCL test (first run) | ~5 min (build + run) | ~8 min (image pull + build + run) |
| NCCL test (cached image) | ~5 min | ~3 min |

**Calibrate per lab during execution.** When the lab says "wait N minutes", plan for ~N/2 — but also set a hard ceiling of 2N before investigating as a genuine stall.

### TRAP 6: Image pull cost dominates first-run timing

Large NVIDIA/NGC container images (e.g., `nvcr.io/nvidia/pytorch:24.12-py3` at ~20GB) take 4-5 minutes to pull on first run even over EC2's internal network. The pod sits in `ContainerCreating` for the full duration. A student (or Claude) watching this may think the pod is stuck.

**Fix:** Before declaring a stall, run `kubectl describe pod <name>` and check the last event. If it's `Pulling image`, just wait. Escalate only if `ImagePullBackOff` appears.

**Where to watch:** Any lab using `nvcr.io/nvidia/*`, `huggingface/*`, Kubeflow training operator images, vLLM runtime images.

### TRAP 7: Cleanup ordering

**NEVER** run `lab-destroy.sh` while managed clusters still exist on the management cluster. CAPA controllers live on the management node; destroying the management infrastructure first orphans all managed cluster AWS resources (EC2, VPCs, NAT gateways, LBs) with no controller left to clean them up.

**Correct order:**
1. `kubectl delete clusterdeployment <name> -n kcm-system` on the mgmt cluster
2. Wait for full deletion (~5-10 min; up to 10 because the k0smotron `K0sControlPlane` finalizer adds a layer beyond CAPI's)
3. Verify AWS-side: `aws ec2 describe-instances --filters "Name=tag:sigs.k8s.io/cluster-api-provider-aws/cluster/<name>,Values=owned"` returns terminated/empty
4. Only then: `./lab-infrastructure/scripts/lab-destroy.sh e2e-val --auto-approve`

### TRAP 8: `lab-refresh-creds.sh` false-positive "CAPA still has credential errors"

**Fixed in commit `d06b56e`.** If running against a pre-fix copy of the script, the trailing health check may erroneously report failure. Verify CAPA health directly with `kubectl logs <newest-capa-pod>` instead of trusting the script's exit message.

```bash

            "Name=instance-state-name,Values=running,pending" \
  --query "Reservations[].Instances[].{id:InstanceId}" --output table

# 6. Preserve S3 state bucket (do NOT use --delete-bucket on lab-destroy.sh)
```

## 🔑 Key Principles Inherited from Lab 5.1 Session

These are the meta-rules that must govern execution:

1. **Empirical-first.** Run the lab as written. Only fix what genuinely breaks under real execution. Don't "fix" intentional design choices (like hardcoded us-east-1 — that's for GPU availability) based on pattern-matching to other clusters.

2. **Atomic commits.** One concern per commit. `fix(lab-5.N): specific thing`. Never bundle "make Task X actually work" with "also polished some wording in Task Y".

3. **Evidence before fixes.** When something fails, gather the actual error message, controller logs, events, and state — BEFORE proposing a fix. This session's Lab 5.1 Task 5 took two rounds of debugging because the first apparent fix (changing the queue label) was necessary but not sufficient; the real fix (adding `kai.scheduler/preemptibility`) only became visible after the first fix exposed the deeper issue.

4. **Preserve root-cause understanding in commits.** Commit messages should explain the root cause in the body, not just "fixed X". Future-you (or a future-Claude) reading the diff should understand *why*, not just *what*.

5. **Verify before declaring done.** After a fix, observe the system and confirm the fix produced the empirical signal you expected (event emitted, counter incremented, state transition occurred) — not just that "things stopped erroring".

6. **Cleanup discipline.** Always managed cluster first, then mgmt cluster. Always verify AWS-side after k8s-side. Never force-remove finalizers as a shortcut.

7. **Don't push without asking.** Commit freely, but push only when the user explicitly asks. Each push is a public, harder-to-reverse action.

8. **When in doubt, pause and report.** The user can always choose to continue; you cannot always undo a wrong choice made silently.
