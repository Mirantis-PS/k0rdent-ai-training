## 🚨 Known Traps (Read Before Executing)

These failure modes were discovered empirically during the Lab 5.1 validation session. Expect them to recur in subsequent labs; apply the fixes preemptively where obvious.

### TRAP 1: STS credential expiration during long labs

**Symptom:** CAPA controller logs emit `RequestExpired` / `AuthFailure` (sometimes labeled "Probable clock skew error"). Cluster provisioning stalls. Deletion stalls in `Terminating but pending` for >5 minutes.

**Root cause:** AWS SSO session tokens typically expire after 1-12 hours. CAPA reads credentials into env vars at process start from `Secret/aws-cluster-identity-secret`. When the STS token expires, CAPA silently cannot call AWS APIs. k0rdent's `Credential.status.ready=true` is a shallow check and does NOT flag the expiration.

**Fix:** Run `./lab-infrastructure/scripts/lab-refresh-creds.sh e2e-val` from the local machine with fresh AWS env vars exported. Script rotates the Secret and restarts CAPA. Reconciliation resumes in ~30 seconds.

**Where to apply during Week 5 execution:** Any lab with unattended waits > 1 hour — particularly labs 5.5 (vLLM, 4h), 5.9 (Kubeflow, 3h), 5.10 (MLflow, 2.5h), 5.16 (distributed training, 4.5h).

**Existing lab doc support:** Lab 5.1 already has this note in Pre-Lab Step 2 and Cleanup after commit `af524d3`. Add equivalent notes to the labs listed above if the empirical run hits the trap.

### TRAP 2: ClusterPolicy ambiguity (NVIDIA GPU Operator vs Kyverno)

**Symptom:** `kubectl patch clusterpolicy/cluster-policy ...` fails with `Error from server (NotFound): clusterpolicies.kyverno.io "cluster-policy" not found`.

**Root cause:** Two CRDs share the short name `clusterpolicy`: `clusterpolicies.nvidia.com` (GPU Operator config) and `clusterpolicies.kyverno.io` (Kyverno policy engine). kubectl picks Kyverno's because `kyverno.io` sorts first in API discovery. Kyverno is deployed as a default k0rdent Service on the `aws-standalone-cp-1-0-20` template, so this bug affects every cluster.

**Fix:** Use the fully-qualified name `clusterpolicies.nvidia.com/cluster-policy` in every `kubectl patch` and `kubectl get` command touching GPU Operator config.

**Where to apply:** Any lab that references `clusterpolicy` or `cluster-policy`. Labs 5.3 (KAI Scheduler tuning), 5.4 (Run:AI), 5.11 (NVIDIA FIPS), 5.13 (TensorRT-LLM) are high-risk because they commonly reconfigure GPU Operator.

**Existing lab doc support:** Fixed in Lab 5.1 by commit `ae22d71`. Grep each lab for `clusterpolicy/cluster-policy` and `kubectl get clusterpolicy cluster-policy` before execution; pre-fix if found.

### TRAP 3: KAI Scheduler preemptibility model

**Symptom:** Preemption tests fail with `NonPreemptibleOverQuota` events on the high-priority pod despite correct K8s PriorityClass + `preemptionPolicy: PreemptLowerPriority` settings.

**Root cause:** KAI Scheduler v0.12.10 has its own preemptibility model (`kai.scheduler/preemptibility` label) orthogonal to Kubernetes PriorityClass. Any workload with K8s priority ≥ 100 defaults to **non-preemptible** in KAI unless the label explicitly says otherwise. The Kubernetes `preemptionPolicy` field is ignored by KAI.

**Fix:** Add `kai.scheduler/preemptibility: "preemptible"` to pod-template labels on workloads that should be evictable.

**Where to apply:** Labs 5.3 (KAI Scheduler), 5.4 (Run:AI — same code path), possibly 5.6 (Troubleshooting GPU — preemption scenarios likely).

**Existing lab doc support:** Fixed in Lab 5.1 Task 5 by commit `d359c8c`. Verify via `kai_total_preemption_attempts` metric after the test — should be ≥ 1.

### TRAP 6: Image pull cost dominates first-run timing

Large NVIDIA/NGC container images (e.g., `nvcr.io/nvidia/pytorch:24.12-py3` at ~20GB) take 4-5 minutes to pull on first run even over EC2's internal network. The pod sits in `ContainerCreating` for the full duration. A student (or Claude) watching this may think the pod is stuck.

**Fix:** Before declaring a stall, run `kubectl describe pod <name>` and check the last event. If it's `Pulling image`, just wait. Escalate only if `ImagePullBackOff` appears.

**Where to watch:** Any lab using `nvcr.io/nvidia/*`, `huggingface/*`, Kubeflow training operator images, vLLM runtime images.

### TRAP 7: Cleanup ordering

**NEVER** run `lab-destroy.sh` while managed clusters still exist on the management cluster. CAPA controllers live on the management node; destroying the management infrastructure first orphans all managed cluster AWS resources (EC2, VPCs, NAT gateways, LBs) with no controller left to clean them up.

**Correct order:**
1. `kubectl delete clusterdeployment <name> -n kcm-system` on the mgmt cluster
2. Wait for full deletion (~5-10 min; up to 10 because the k0smotron `K0sControlPlane` finalizer adds a layer beyond CAPI's)
3. Verify AWS-side: `aws ec2 describe-instances --filters "Name=tag:sigs.k8s.io/cluster-api-provider-aws/cluster/<name>,Values=owned"` returns terminated/empty
4. Only then: `./lab-infrastructure/scripts/lab-destroy.sh e2e-val --auto-approve`

### TRAP 9: `lab-provision.sh` does NOT create the k0rdent credential chain

**Discovered during Lab 5.2 validation (2026-04-14/15 session).**

**Symptom:** On a freshly-provisioned mgmt cluster (no prior Week 1 labs run), `kubectl get credentials -n kcm-system` returns empty. Applying a `ClusterDeployment` that references `credential: aws-cluster-identity-cred` fails because the Credential resource does not exist.

**Root cause:** `lab-provision.sh`'s `05-configure-providers.sh` step only creates a *placeholder* `aws-credentials` secret with the literal string `REPLACE_WITH_YOUR_ACCESS_KEY`. The real 4-resource credential chain (`Secret/aws-cluster-identity-secret` + `AWSClusterStaticIdentity/aws-cluster-identity` + `ConfigMap/aws-cluster-identity-resource-template` + `Credential/aws-cluster-identity-cred`) is expected to come from Week 1 Lab 1.3. `lab-refresh-creds.sh` updates the first resource but does not create the other three.

**Workaround in this session:** After provisioning, apply all 4 resources manually on the mgmt node, using `$AWS_ACCESS_KEY_ID` / `$AWS_SECRET_ACCESS_KEY` / `$AWS_SESSION_TOKEN` from the local env:

```bash
kubectl create secret generic aws-cluster-identity-secret -n kcm-system \
  --from-literal=AccessKeyID="$AWS_ACCESS_KEY_ID" \
  --from-literal=SecretAccessKey="$AWS_SECRET_ACCESS_KEY" \
  --from-literal=SessionToken="$AWS_SESSION_TOKEN"

kubectl apply -f - <<EOF
apiVersion: infrastructure.cluster.x-k8s.io/v1beta2
kind: AWSClusterStaticIdentity
metadata:
  name: aws-cluster-identity
  labels:
    k0rdent.mirantis.com/component: "kcm"
spec:
  secretRef: aws-cluster-identity-secret
  allowedNamespaces: {}
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: aws-cluster-identity-resource-template
  namespace: kcm-system
  labels:
    k0rdent.mirantis.com/component: "kcm"
---
apiVersion: k0rdent.mirantis.com/v1beta1
kind: Credential
metadata:
  name: aws-cluster-identity-cred
  namespace: kcm-system
spec:
  identityRef:
    apiVersion: infrastructure.cluster.x-k8s.io/v1beta2
    kind: AWSClusterStaticIdentity
    name: aws-cluster-identity
    namespace: kcm-system
EOF
```

**Separately worth fixing:** teach `lab-provision.sh` to create the full chain when real AWS env vars are present so Labs 5.2+ don't require running Lab 1.3 first. Out of scope for the Week 5 empirical pass; flag in findings for a follow-up plan.

### TRAP 10: kgst OCI version-tag prefix mismatch fails with opaque `verify-job BackoffLimitExceeded`

**Discovered during Lab 5.2 Task 2.**

**Symptom:** `helm upgrade --install <name> oci://ghcr.io/k0rdent/catalog/charts/kgst --set "chart=<chart>:<version>"` fails with:

```
Error: failed pre-install: 1 error occurred:
  * job verify-job-<chart>-<version-slug> failed: BackoffLimitExceeded
```

The error is opaque; the actual cause is only visible via `kubectl logs -n kcm-system job/verify-job-<name>`, which typically reads `Chart oci://ghcr.io/k0rdent/catalog/charts/<chart>:<version>: not found`.

**Root cause:** kgst passes the version string straight through to the OCI registry, and each catalog chart mirrors its upstream project's tag convention:

- `v` prefix: `kserve:v0.15.0`, `kserve-crd:v0.15.0` (KServe upstream tags `v0.15.0`)
- NO `v` prefix: `gpu-operator:25.10.0`, `mlflow:1.8.1`, `kuberay-operator:1.5.1`, `cert-manager:1.17.2`

**Fix:** When writing a new `kgst` install command, verify the chart's upstream release-tag convention before picking the prefix. For labs that hard-code a chart install, check on [catalog.k0rdent.io](https://catalog.k0rdent.io/) first.

**Where to apply during Week 5 execution:** Every lab that installs catalog charts via `kgst`. High risk: Labs 5.5 (vLLM), 5.7 (JupyterHub), 5.8 (Vector DB), 5.9 (Kubeflow), 5.10 (MLflow), 5.13 (TensorRT-LLM).

**Also note** after a failed verify-job, the Helm release is left in a half-created state — must `helm uninstall <name> -n kcm-system` AND `kubectl delete job verify-job-... -n kcm-system` before retrying with the correct version.

### TRAP 11: Sveltos silently overwrites values when adopting an existing helm release

**Discovered during Lab 5.2 Task 3.**

**Symptom:** A `MultiClusterService` references a `ServiceTemplate` whose release name + namespace match a helm release that was previously installed manually on the workload cluster (e.g. `helm install gpu-operator ... -n gpu-operator` from Lab 5.1 Pre-Lab). Sveltos's addon-controller **adopts** the existing release (its ClusterSummary shows `status: Managing`) and runs a `helm upgrade` using the ServiceTemplate's *default* chart values — not the values of the original install. Any customization passed to the original install (e.g. k0s `toolkit.env` paths) is silently dropped.

**Consequence in Lab 5.2:** Lab 5.1 installs gpu-operator with k0s-specific `CONTAINERD_CONFIG=/etc/k0s/containerd.d/nvidia.toml` etc. Lab 5.2's MCS adopts it and re-rolls with default values, breaking the nvidia runtime class. `nvidia-container-toolkit-daemonset` flaps with `FailedCreatePodSandBox: no runtime for "nvidia" is configured`; GPU allocatable drops from 4 to 0.

**Fix options:**
1. **Don't include the adopted release in the MCS.** Leave manual installs manual; use the MCS only for genuinely-new services. (Chosen in Lab 5.2 fix `4442e2c`.)
2. **Pass full values in the MCS.** `values: |` block in the MCS service entry with the same k0s-specific overrides. Requires keeping values in sync between Lab 5.1's helm install and Lab 5.2's MCS.

**Where to apply during Week 5 execution:** Any lab that adds MCS entries for services deployed in earlier labs. Labs 5.3 (KAI), 5.6 (Troubleshooting), 5.11 (FIPS) all reconfigure GPU Operator and could repeat the same class of bug.

### TRAP 12: Deleting a ClusterSummary cascade-uninstalls all managed helm releases

**Discovered during Lab 5.2 Task 3 debugging.**

**Symptom:** `kubectl delete clustersummary <name> -n kcm-system` — intended as a "force Sveltos re-reconcile" nudge — causes Sveltos to treat all `helmReleaseSummaries` in that ClusterSummary as unmanaged and run `helm uninstall` on each of them. The workload cluster loses every MCS-deployed release; recovery takes another full reconcile cycle.

**Safer alternative:** Trigger re-reconcile via annotation on the owning `Profile`:

```bash
kubectl annotate profile <profile-name> -n kcm-system \
  reconcile.projectsveltos.io/trigger="$(date +%s)" --overwrite
```

Or just wait out the Sveltos reconcile interval (~60-90 s per cycle).

**Lesson:** ClusterSummary is a derived resource — treat it as read-only. Mutation forces a hard reset of managed state.

### TRAP 13: Stale ServiceAccount token after KAI `helm upgrade --set global.gpuSharing=true`

**Discovered during Lab 5.3 Task 4 validation (see commit `71a4f47`).**

**Symptom:** After `helm upgrade kai-scheduler --set global.gpuSharing=true`, every fractional pod stays `Pending` forever. Scheduler log floods with `ERROR status_updater/concurrency.go:117 Failed to update pod group status <ns>/<name>: Unauthorized`. `kubectl auth can-i update podgroups/status --as=system:serviceaccount:kai-scheduler:scheduler` still returns `yes` — so RBAC is correct; the failure is at *authentication*.

**Root cause:** The helm upgrade deletes and recreates every ServiceAccount in the `kai-scheduler` namespace. Six of seven component pods (admission, binder, pod-grouper, podgroup-controller, queue-controller, operator) have a pod-template change triggered by the flag and rollover naturally — their new pods mount tokens for the new SA UIDs. The scheduler's pod template is NOT modified by `gpuSharing=true`, so no rollover happens; the pod keeps running with a token bound to the now-deleted SA UID. API server rejects every `PodGroup.status` update.

**Fix:** Add an explicit `kubectl rollout restart deployment/kai-scheduler-default -n kai-scheduler` step immediately after the helm upgrade. Committed at `71a4f47` in Lab 5.3 Task 4 Step 1.

**Where to apply:** Any lab that calls `helm upgrade` on an existing KAI install with feature flags. Labs 5.4 (Run:AI — same chart family), potentially 5.6 (Troubleshooting GPU if scheduler reconfigured).

### TRAP 14: KAI parent-queue quota must cover non-preemptible children

**Discovered during Lab 5.3 Task 6 validation (see commit `68d0b55`).**

**Symptom:** Non-preemptible workload (K8s PriorityClass `value ≥ 100`) refuses to schedule with `NonPreemptibleOverQuota: Non-preemptible workload is over quota. Workload requested N GPUs, but <parent-queue> quota is 0 GPUs, while 0 GPUs are already allocated for non-preemptible pods.` Even though the leaf queue's own `quota` field is sufficient for the request.

**Root cause:** KAI enforces the non-preemptible quota check at *every* ancestor queue in the hierarchy, not just the leaf. Non-preemptible workloads are forbidden from using over-quota resources. A common mental model — "cluster-root has quota 0, distributes to children" — breaks for non-preemptible workloads: they can only use their leaf's quota, and that quota is only valid if every ancestor's quota is ≥ the sum of children's quotas.

**Fix:** Set every ancestor queue's `spec.resources.<resource>.quota` to at least the sum of that ancestor's direct children's quotas. For the Lab 5.3 sample hierarchy (`training-queue=2, inference-queue=1, research-queue=1`), `cluster-root.spec.resources.gpu.quota` must be `>=4`.

**Where to apply:** Labs 5.4 (Run:AI — shares queue semantics via inherited scheduler), 5.6 (Troubleshooting GPU if it reconfigures queues), and any future lab that establishes a multi-level KAI/Run:AI hierarchy.

### TRAP 15: `batch/v1` Jobs do NOT gang-schedule on KAI v0.14.0

**Discovered during Lab 5.3 Task 5 validation (see commit `ca5ee73`).**

**Symptom:** A Job with `parallelism: N` submitted to KAI creates N separate `PodGroup` resources (one per pod, `minMember: 1` each) instead of one shared PodGroup with `minMember: N`. Pods bind one-by-one as GPUs become available, not atomically.

**Root cause:** KAI v0.14.0's PodGrouper BatchJob plugin emits "legacy" per-pod PodGroups. Gang semantics (atomic all-or-nothing scheduling) are only applied when PodGrouper recognizes the owner as a dedicated gang-workload CRD: `PyTorchJob`, `TFJob`, `MPIJob`, `XGBoostJob` (Kubeflow Training Operator), `RayCluster`, `RayJob` (KubeRay), or a manually pre-created `PodGroup` referenced via `pod-group-name` annotation.

**Fix:** Either install a Kubeflow or KubeRay operator to bring the relevant gang-scheduling CRDs, or manually pre-create a `PodGroup` with the desired `minMember` and set `pod-group-name: <pg-name>` as an annotation on every pod in the group. The lab's Task 5 Step 2 Kubernetes Job example CANNOT demonstrate true gang scheduling without one of these — it demonstrates parallel scheduling only.

**Where to apply:** Lab 5.9 (Kubeflow — provides the required CRDs), Lab 5.16 (Distributed Training — must use PyTorchJob or equivalent, not plain Job).

### TRAP 17: Prometheus `foo:bar` metric names incompatible with K8s HPA DNS-1123 validation

**Discovered during Lab 5.5 Task 6 validation (see commit `ff19ab0`).**

**Symptom:** HPA spec referencing a Prometheus-native metric name with a colon separator (e.g. `vllm:num_requests_waiting`, `kube_pod_container_resource_limits:gpu`) is rejected by the K8s API server with DNS-1123 validation error, OR — if referenced with underscore substitution like `vllm_num_requests_waiting` — the HPA controller reports `FailedGetPodsMetric: the server could not find the metric for pods` even though the custom-metrics API exposes it as `pods/vllm:num_requests_waiting`.

**Root cause:** vLLM (and several other modern Prometheus exporters) use `:` as a logical-namespace separator in metric names. prometheus-adapter's default configuration preserves the `:` when proxying to the `custom.metrics.k8s.io/v1beta1` API, surfacing metrics as `pods/vllm:X`. Kubernetes HPA `metric.name` is validated as a DNS-1123 label (lowercase alphanumerics, hyphens, dots — NO colons), so no HPA can reference `vllm:X` directly. Adapter default rules don't rewrite the colon.

**Fix:** Add a prometheus-adapter rule that rewrites `vllm:X` → `vllm_X` (or any `foo:X` → `foo_X`) at exposure time:

```bash
helm upgrade prometheus-adapter prometheus-community/prometheus-adapter \
  -n monitoring --reuse-values \
  --set-json 'rules.custom=[{
    "seriesQuery": "{__name__=~\"^vllm:.*\"}",
    "resources": { "template": "<<.Resource>>" },
    "name": { "matches": "^vllm:(.+)$", "as": "vllm_$1" },
    "metricsQuery": "sum(rate(<<.Series>>{<<.LabelMatchers>>}[2m])) by (<<.GroupBy>>)"
  }]'
kubectl rollout restart deployment/prometheus-adapter -n monitoring
```

Committed at `ff19ab0` as a Task 6 Prerequisite in Lab 5.5.

**Where to apply:** Any lab with an HPA against a Prometheus custom metric. Lab 5.9 (Kubeflow Pipelines autoscaling), Lab 5.10 (MLflow inference autoscaling), potentially Lab 5.7 (Jupyter notebook autoscaling if covered).

### TRAP 18: `kubectl debug node/` default `--profile=legacy` lacks CAP_SYSLOG

**Discovered during Lab 5.6 Scenario E validation (see commit `fe295f7`).**

**Symptom:** `kubectl debug node/<name> -it --image=ubuntu -- bash -c "dmesg | grep ..."` fails with `dmesg: read kernel buffer failed: Operation not permitted`. The debug pod is created, chroots into the host namespace, but `dmesg` cannot read `/dev/kmsg`.

**Root cause:** kubectl ≥1.30 defaults `kubectl debug` to `--profile=legacy`, which grants only `CAP_SYS_PTRACE` and issues a deprecation warning. Ubuntu 22.04 nodes enforce `kernel.dmesg_restrict=1`, which requires `CAP_SYSLOG` to read the kernel ring buffer. `chroot /host` does NOT change capabilities — only filesystem root. The debug pod remains unable to dmesg.

**Fix:** Use `--profile=sysadmin`, which grants `CAP_SYSLOG` + `CAP_SYS_ADMIN` + `CAP_SYS_PTRACE` + `CAP_NET_ADMIN` (see [profile source](https://github.com/kubernetes/kubectl/blob/master/pkg/cmd/debug/profiles.go)):

```bash
kubectl debug node/$NODE_NAME -it --profile=sysadmin --image=ubuntu \
  -- bash -c "dmesg | grep -i 'xid\|nvidia' | tail -20"
```

**Where to apply:** Any lab using `kubectl debug node/` for node-level host diagnostics. Lab 5.6 (GPU hardware faults), potentially Lab 5.11 (FIPS — may inspect kernel module state), Lab 5.15 (RDMA — likely inspects `ibstatus`, `dmesg | grep mlx5`).

### TRAP 19: Gated Hugging Face models silently fail with 401, look like the scenario's advertised failure

**Discovered during Lab 5.6 Scenario C validation (see commit `963a842`).**

**Symptom:** vLLM (or other HF-model-consuming) pod crashes shortly after container start, before reaching the failure mode the lab is trying to teach (OOM, probe timeout, etc.). Logs show:

```
OSError: You are trying to access a gated repo.
401 Client Error. Cannot access gated repo for url
  https://huggingface.co/meta-llama/Llama-2-13b-chat-hf/resolve/main/config.json.
Access to model meta-llama/Llama-2-13b-chat-hf is restricted.
```

**Root cause:** `meta-llama/*`, `mistralai/Mistral-*-Instruct`, and similar are gated on Hugging Face — downloading them requires (a) an HF account, (b) access granted by the model owner, (c) an `HF_TOKEN` secret mounted into the pod. **Fix:** Prefer the Nous Research ungated mirrors (`NousResearch/Llama-2-7b-chat-hf`, `NousResearch/Llama-2-13b-chat-hf` — same weights, same architecture, identical memory math). Or make the HF_TOKEN a hard prerequisite with a `kubectl create secret generic hf-token --from-literal=token=hf_...` recipe in the lab's Pre-Scenario section.

**Where to apply:** Grep each Week 5 lab for `meta-llama/`, `mistralai/`, `google/gemma-`, `microsoft/phi-` in manifests:

## 🔑 Key Principles Inherited from Lab 5.1 Session

These are the meta-rules that must govern execution:

1. **Empirical-first.** Run the lab as written. Only fix what genuinely breaks under real execution. Don't "fix" intentional design choices (like hardcoded us-east-1 — that's for GPU availability) based on pattern-matching to other clusters.

2. **Atomic commits.** One concern per commit. `fix(lab-5.N): specific thing`. Never bundle "make Task X actually work" with "also polished some wording in Task Y".

3. **Evidence before fixes.** When something fails, gather the actual error message, controller logs, events, and state — BEFORE proposing a fix. This session's Lab 5.1 Task 5 took two rounds of debugging because the first apparent fix (changing the queue label) was necessary but not sufficient; the real fix (adding `kai.scheduler/preemptibility`) only became visible after the first fix exposed the deeper issue.

4. **Preserve root-cause understanding in commits.** Commit messages should explain the root cause in the body, not just "fixed X". Future-you (or a future-Claude) reading the diff should understand *why*, not just *what*.

5. **Verify before declaring done.** After a fix, observe the system and confirm the fix produced the empirical signal you expected (event emitted, counter incremented, state transition occurred) — not just that "things stopped erroring".

6. **Cleanup discipline.** Always managed cluster first, then mgmt cluster. Always verify AWS-side after k8s-side. Never force-remove finalizers as a shortcut.

7. **Don't push without asking.** Commit freely, but push only when the user explicitly asks. Each push is a public, harder-to-reverse action.

8. **When in doubt, pause and report.** The user can always choose to continue; you cannot always undo a wrong choice made silently.
